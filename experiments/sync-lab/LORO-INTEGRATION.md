# Loroを入力・端末保存・通信へ接続する

0.6.0の独立した30行の試作。`/?engine=loro&doc=demo&input=bound&tree=1` で開く。
`loro-crdt@1.17.1` に加え、公開済みの `loro-codemirror@0.3.3` を固定した。
本番とは別のIndexedDB・ファイル・文書IDを使う。方式の採用・データ移行ではない。
実行した件数とCIのコードは [RESULTS.md](RESULTS.md) を正とする。

## 縦につないだ範囲

ブラウザーのLoroDocとCodeMirror → 専用IndexedDB → ローカル限定のHTTP API →
Loroの実際のバイナリを保存するファイル、という経路を動かす。
3端末は独立したブラウザーcontextを使い、全行と属性をサーバー保存の読み直しまで照合する。
行IDの索引を作り、エディターが本文を探すたびに全ノードを走査することを避けた。
表示やsnapshotの生成にはまだ全体の走査がある。

端末は初期JSONを作り直さず、保存したsnapshot・因果上の先行更新を待つ受信バイナリ・
未確認の送信を同じIndexedDB取引で戻す。初回の合成文書はサーバーで一度だけ作る。
読み取りやバイナリの取り込みに失敗しても、空の成功結果へフォールバックしない。
初回の圏外起動に文書がなければ合成文書を勝手に作ったり送ったりしない。

## 保存と送信の順序

1. ローカルの編集更新を送信待ちへ加え、snapshot・待機中の受信・送信待ちを一取引で保存する。
2. 保存完了待ちの間に次の編集が増えた場合も、増えた分の確定まで待ってから送る。
3. APIは文書ごとに直列化し、毎回保存ファイルから候補文書を読み、バイナリを取り込む。
4. 壊れた更新を含む要求は候補だけを破棄する。正しく処理できた場合はファイルを置換してから応答する。
5. 応答した分だけを送信待ちから除き、受信内容と残りの待ちを端末の一取引で保存する。

通信待ちに次の入力が増えても、先の応答で後の入力を除かない。
保存成功の返事を失い、送信待ちを残したまま開き直しても、同じ操作IDのバイナリ更新が
重複適用されて増えないことを確認する。サーバー保存の成功前に送信待ちを完了しない。
保存取引の中止についても、以前の三つのデータが部分更新されないことを試す。

APIは認証のない合成データ専用で127.0.0.1に限定する。
今回は100ms間隔のHTTP交換と小さいファイル保存であり、Loro公式の同期サービスの比較ではない。
実験の上限は1要求1MB・更新1000個。大きい圏外キューの分割と調整はまだ実装していない。
毎編集の全snapshot保存、毎回の保存ファイル読み直し、待ちのない100msの照会は、
本番用の効率・電池消費・サーバー運用の設計として採用したものではない。

## エディターへの接続

文字の差分処理と変換中の受信は公式のCodeMirror接続へ任せる。
ブラウザー側は公開されているweb版のWASMを通常の静的アセットとして初期化し、
Base64を大きいJavaScriptへ埋め込む形を避けた。NodeのAPIと単体試験はNode版を使う。
固定した0.3.3には次の条件を実部品で再現したため、小さいアダプターを置いた。

- 初期値が同じとき、フォーカス等の空更新を挟まない最初の直接変更が読み飛ばされる条件。
  初期化完了用の空更新を先に通す。通常のフォーカス操作が入る試験だけでは再現しなかったため、
  実EditorStateと公式接続を使う単体で条件を分離している。
- 受信の一取引に属性・木・二行の本文が混じると、別の対象のイベントで処理が終了して
  入力欄の表示が取り残される条件。対象行の文字イベントだけを公式接続に渡す。

アダプターはCRDTやIMEの統合アルゴリズムを作り直すものではない。
公式接続の版を上げるときは、再現試験を確認し、不要になった適応を外す。
`binding=raw` は素の接続との対照試験専用であり、通常の検証画面には付けない。

UndoManagerは文書ごとに一つとし、自分の入力・移動・削除印だけを対象にする。
各入力欄がUndoのコールバックを上書きせず、行IDと安定したカーソルを一つの接続で管理する。
別端末の追記を残し、Undo/Redoで編集した行と選択範囲へ戻ることも試す。
削除は [LORO.md](LORO.md) と同じ印方式。素のTree削除は本文を再作成する問題があるため使わない。

## WebKitの画面更新

画面を離れた古い文書が照会を始めないよう、beforeunloadで早めに通信とタイマーを止め、pagehideでも停止する。
BFCacheから復帰する場合は、元が接続中だった文書だけ接続を戻す。
データや通信状態が同じなら描画の通知を省き、通信状態だけの変化で枝のボタンを作り直さない。
同じ内容のポーリングで対象DOMが外れ続け、WebKitでボタンを押せなかったケースの対策。
エラーを試験から除外したり、クリックを強制したりして合格にしない。

## 残る限界と次の区切り

- ChromiumのIMEは入力プロトコル、WebKitはDOMイベント列。実OSの候補選択ではない。
- 同期通信だけを切る。HTTP画面は取得でき、Service Workerは無効。実機PWAの圏外起動ではない。
- 30行での接続を確認する段階。1万行の表示・端末保存・別端末反映の負荷は次に測る。
- 同じ保存領域を使う複数タブの同時利用は未対応。今回は独立したcontextで試す。
  本番採用前には保存領域の所有者の保証や、更新を上書きしない共有方式も必要。
- 削除済みの親への古い移動は、本文を保っても削除済み欄へ入る。枝単位の競合UXは残る。
- 取引中止の試験はディスク故障や容量不足時の製品の復旧導線を完成させたものではない。
- 認証・権限、実際の同期サービスの運用・費用、電源断、PWA更新、旧データ移行は未検証。
  サーバーの保存自体を失った場合の修復も、この実験用HTTP経路では確認していない。

この接続を同じ条件で比較できた後、1万行の全体負荷と独自コード・運用の比較を行い、
一つの方式の推薦を最初の意思決定の区切りにする。毎回のJSON退避や全体停止は採用条件にしない。
