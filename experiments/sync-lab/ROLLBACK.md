# 最新の編集を維持する切り戻し

0.19.0。初回導入で戻す単位は、新同期に接続したアプリの配信成果物とする。
接続先・文書UUID・移行世代・ネイティブ履歴・未送信・旧書き込み停止は維持する。
これで切替後の編集を古いJSONや旧DBへ戻す逆変換を避け、端末ごとの続きも同じ履歴へ合流できる。

## 検証した互換性

0.18.0の固定コミット`3ef9a0d1aedde4491b22b236ecaf36ba714291e2`から、独立したfixture用ビルドを作る。
既存の同じlockfileの依存を参照し、ネットワークから新しい依存は入れない。
生成物は`.data/rollback-0.18.0/`だけに置き、固定refと全ファイルのSHA-256をmanifestへ残す。
出力フォルダーが既にあれば作り直さず、元のコード・控え・データは上書きしない。

```powershell
pnpm prepare:rollback
$env:LAB_VERIFY_ROLLBACK = '1'
pnpm test tests/outline-recovery.spec.js
```

合成Auth/RPCと実Outliner・IndexedDB・Web Locksで次を確認する。

1. 最新版で自動切替を完了し、控えの未送信を復元して同期する。
2. 同じオリジン・同じ端末保存で0.18.0のビルドへ戻り、復元後の本文を開く。
3. 旧ローカルの書き手を止めるロックと移行完了印を維持し、0.18.0で追記・送信する。
4. 最新版へ戻って両方の追記を読み、同じ控えを選び直しても再送しない。

ChromiumとWebKitの双方でこの往復を検査する。
このfixtureビルドそのものを本番へ配信しない。本番の接続設定・通常起動入口・PWAの配信切替は③の条件になる。

## 本番リリース時に確保するもの

リリース担当は実行前に以下を一組で保管する。今回これらを本番へ適用してはいない。

- 新しい配信成果物と、同じ本番接続設定・文書・新Providerを使う互換の配信成果物。
  ソースのrefと成果物のハッシュを記録する。
- 旧書き込み停止後に確定した共通原本と、各端末に残る未送信の控え。
- 新DBの初期原本・確定ログと、移行先・移行世代の記録。切替後も原本とログを維持する。

実配信のリハーサルでは、同じ本番オリジンと保存名を維持して互換成果物へ切り替え、
PWAの更新後も保存済みの本文・未送信・画像参照を開き、その版で追記した内容を最新版へ持ち帰る。
ブラウザーのストレージ削除や端末保存の作り直しを手順に含めない。

切り戻しの際も`legacy_cutover.phase = active`と旧書き込みの拒否を維持する。
古い端末からの全件保存を再開させるためのトリガー解除や、旧同期版への単純な切替は行わない。
同期プロトコルを旧方式へ逆移行する作業は、今回の本番導入の対象に含めない。

## 次の区切り

0.21.0で本番向けの通常入口・既存ログイン・停止確認付き起動を実装した。
通常PWAの配信更新試験では、この入口を備える0.21.0以降の固定コミットを互換成果物の基準にする。
同じ接続・所有者・文書・認証保存を使い、最新版での未送信を残したまま往復する。
上の0.18.0は履歴とクライアントの互換性を確かめる検証用で、通常PWAの配信先として扱わない。

②で端末復元とクライアント互換性の経路を揃えた。
③で最新の全体CI、実Supabase・GAS、本番接続設定の切替リハーサル、実Outliner一万行、三端末PWA・IMEを確認する。
本番での配信切替・SQL適用・データ移行を、このローカルの成功だけで完了扱いにしない。
