# 独自実装と運用の比較（2026-10-26）

速いライブラリーを選んでも、利用者に復旧操作を求める設計が残れば今回の目的を満たさない。
ライブラリーが担う部分と、Task Space側が維持する部分を分ける。
対象はこの検証室の固定バージョンと構成。一般的な製品の優劣や費用の比較ではない。

| 分担 | Yjs + Hocuspocus | PowerSync + Postgres | Loro + 今回のHTTP交換 |
| --- | --- | --- | --- |
| 本文の変更統合・自分のUndo | Y.Textと既存のCodeMirror接続 | 列の値を照合する独自API、下書き・履歴も独自。本文同士は別案になる | LoroTextとUndoManager。CodeMirrorの複数行イベント・選択位置の接続アダプターは独自 |
| 枝の移動 | 親ID方式では循環回復が独自に必要 | 文書ロック、最新の木の検査、拒否した移動の保全を独自APIで行う | LoroTreeが並行移動の循環を処理。削除印の意味と復元表示はアプリの責任 |
| 端末保存 | y-indexeddbがバイナリ更新を保存 | SDKがSQLiteと送信待ちを管理 | snapshot・未適用更新・送信待ちの一体保存を独自実装 |
| 送受信と再送 | Hocuspocus。受信確認と永続保存の確定は別 | SDKの配信・再送 + 独自APIの操作IDとDB取引 | 100msごとのHTTP交換、返事を失った再送、保存後の送信待ち除去を独自実装 |
| サーバーの構成要素 | 常駐同期サービス + 永続ストア | ソースDB + 論理レプリケーション + PowerSync + 内部ストア + 書込みAPI | 現状は常駐Node API + ファイル。製品向けの運用設計は未実装 |
| 日常の確認操作へ戻り得る点 | 循環・削除済み親への移動、意味が両立しない本文変更 | 別々の追記でも同じ本文列の競合になり、確認が必要 | 削除済み親への移動、意味が両立しない本文変更。CRDTの収束だけでは解決しない |

既存Postgresとの近さだけでPowerSync案を選ぶと、今回避けたい本文競合の判断と回復を、
引き続きアプリ側で作ることになる。Yjs案では本文の既存接続を使える一方、今の親IDモデルのままでは
木の循環対処が必要になる。Loro案は本文と木の両方の統合を既存型へ寄せられるが、
0.6.0の通信・端末保存は比較のための独自実装であり、これをそのまま採用すると別の保守負担が残る。

## 三案に共通して製品へ移す前に必要なこと

- 認証した本人だけが文書を取得・更新できること。固定の検証ユーザーやループバック接続は本番の権限試験ではない。
- 端末の保存確定と送信待ちの確定を同じ世代で扱い、サーバーも永続化してから完了を返すこと。
  接続中・受信済み・送信待ちなしのどれも、それだけで全端末と保存先の確定を意味しない。
- PWAの休止・圏外起動・更新・容量不足、同じ端末の複数窓、サーバー再起動と復旧。
- 端末ごとの未送信内容を含む移行と、既存データへ戻せる手順。画像とDriveの控えは同期とは別の責任として扱う。
- 同じ箇所の意味が両立しない編集だけを両方残すこと。通常の別端末への持ち替えで全体を止めない。

これらは試験の件数やソース行数では代替できない。サービスの監視・バックアップ・復元手順、
費用見積りも本番構成を決めてから行う。今回のファイルのバイト数をクラウド費用に換算しない。

## 一次資料との対応

Loroの[永続化の手引き](https://loro.dev/docs/tutorial/persistence)は、頻繁な差分保存と定期的なsnapshotの組合せを示している。
今回の毎編集の全文snapshotは導入を簡単にする試作で、推奨される最終形とは違う。
同じ世代として保存する保証を保ちつつ、差分の追記と圧縮へ移せるかを別途検証する。

Hocuspocusの[Database拡張](https://tiptap.dev/docs/hocuspocus/server/extensions/database)は保存したYjsバイナリを読み戻す構成を前提とする。
毎回JSONから文書を作り直さない。保存は[store hook](https://tiptap.dev/docs/hocuspocus/server/hooks)で行い、
今回のdebounceされた保存完了と端末の送信待ち完了を混同しない。

[PowerSyncの構成説明](https://powersync.com/)では、端末の書込みをSQLiteへ反映してからバックエンドAPIへ送る。
変更の意味を判定する独自APIは、配信サービスを採用しても必要になる。

Loroには[公式Protocol実装](https://github.com/loro-dev/protocol)とWebSocketクライアント、最小サーバーがある。
今回のHTTP交換の代替候補だが、この検証室には未導入で、性能や保存保証は未検証。
接続・分割送信の仕組みがあっても、ACKをサーバー永続化完了として扱えるかは保存経路を含めて確かめる。
公式の最小サーバーへ置き換えるだけで運用・認証・復旧が完成したとは扱わない。
