# 本人認証と保存確定の境界（0.11.0）

0.12.0の既存ログイン画面・SDKからの接続は[SESSION-INTEGRATION.md](SESSION-INTEGRATION.md)を参照。

認証と通信の部品を替える前に、「誰の文書を扱うか」と「いつ送信待ちを消してよいか」を、
既存のHTTP比較経路で独立して検査する。本番へこのポーリングやファイル保存を採用する決定ではない。

## 本人だけを通す

`scripts/owner-server.mjs`はループバックの別HTTPサーバーを作る。
接続先のAuth、公開APIキー、所有者ID、許可する文書IDをサーバー設定で固定する。
`/lab/owner-loro/`の読込み・書込みの両方を検査し、拒否した要求から文書ファイルを生成しない。
認証関数を渡さずにこの経路を作る設定は起動時に拒否する。
従来の無認証比較用`/lab/loro/`をこのサーバーへ同居させない。

署名やパスワード検証を新作せず、[Supabase AuthのGet a user](https://supabase.com/docs/reference/javascript/auth-getuser)
に対応する固定URLの`GET /auth/v1/user`へBearerを渡し、その検証済み利用者IDを使う。
端末が申告したIDやJWTの未検証payloadを権限判定に使わない。接続先のリダイレクトも追わない。
HTTPSを必須とし、ループバックHTTPは試験用の明示設定だけ許可する。
Authの許可をキャッシュせず、Authが拒否した認証を次の要求へ使い回さない。
この構成では要求ごとにAuthへの往復が増える。100msポーリングと組み合わせたまま製品へ持ち込まない。
本体には`src/AuthGate.jsx`の既存ログインと`onAuthStateChange`がある。
製品へ移すときはこのセッションを使い、別のログイン画面を増やさない。
公開接続キーを所有者のBearerとして流用せず、既存セッションの取得・更新・ログアウトを同期経路へ接続する。

端末は認証SDKから取得する関数を通信部品へ渡す。トークンを文書・URL・IndexedDBへ保存しない。
401は一度だけ新しい認証で同じ差分を再送し、なお401、または403なら送信を止める。
Auth障害の503や通信停止は、500msから最大15秒へ間隔を延ばして再試行する。
本文と送信待ちを初期化せず、日常の通信エラーからJSON退避や全体の競合表示へ進まない。
認証状態が戻った後の`connect()`は同じ送信待ちを使う。本体の認証状態イベントへの接続は次の工程。

認証経路の端末保存名は`owner:<利用者ID>:<文書ID>`を含む専用名にする。
同じブラウザーで別利用者の文書を開いても、前の本文や未送信を読込み・送信しない。
これは利用者ごとの保存の分離で、端末内暗号化や、本体のログアウト画面まで完成した意味ではない。

## 保存できるまで完了を返さない

サーバーは毎回保存済みの履歴から候補を読み、文書単位のキューで処理する。
更新を取り込んだメモリーを、次の要求へ保存済みとして使い回さない。
snapshotと未適用受信を一体で一時ファイルへ書き、ファイルの`fsync`、置換を待ってから200を返す。
POSIXではディレクトリーの`fsync`も待つ。Windowsはディレクトリーの`fsync`がないため、
今回のプロセス強制終了からの復元と、OSや装置の電源断の保証を区別する。
一つのプロセス内の文書キューであり、複数サーバー間の書込みロック・DB取引を実装したものではない。

端末は既存の保存順を保つ。

1. 編集差分と送信待ちを、同じIndexedDB取引に確定する。
2. 保存が終わった差分だけを送る。
3. サーバーの保存成功と、壊れていない応答の全部分を確認する。
4. 受信差分と送信したIDの完了を、同じ端末取引で確定する。

サーバー保存前に落ちたら端末から再送する。保存後の返事だけを失っても、再送した同じCRDT操作は重複しない。
再送した更新が文書に取り込み済みでも、保存確定の処理は改めて行う。
置換後の保存確認だけが失敗した場合に、次の要求がファイルを読めたことだけで成功扱いするのを防ぐ。
保存失敗では以前のファイルを先に削除しない。壊れた保存を空の文書として成功扱いしない。

## 試験で確認する範囲

`tests/loro-owner.spec.js`はChromiumとWebKitで、それぞれ別のNode子プロセスの実HTTP APIと実ファイルを使う。
Authだけは使い捨ての応答サービスに置き換える。トークン発行・障害注入は試験プロセス内に閉じる。
本物のSupabaseへログインした試験や、JWT署名・期限の検証器を試作したものではない。

| 場面 | 確認内容 |
| --- | --- |
| 本人の二端末 | 開くだけでは変更せず、圏外の本文と別端末の属性が合流する |
| 未認証・偽のトークン・別利用者・許可外文書 | 読込みと書込みを拒否し、文書ファイルも生成しない |
| 認証の失効とAuth障害 | 再認証中も入力を保存し、圏外再読込み後に元の編集を送る |
| 同じブラウザーの利用者切替 | 前の本文と未送信を渡さず、本人へ戻ると未送信を再開する |
| 保存途中でサーバーを強制終了 | 送信待ちを消さず、再起動後に一度だけ反映する |
| 保存後に返事を失い、さらに強制終了 | サーバーと端末の両方から復元し、重複せず別端末にも届く |

単体試験では`fsync`失敗・ファイル置換失敗・置換後の確定失敗とその再送、固定した認証先、壊れたAuth応答、
一度だけの認証更新、トークンをURLや本文へ混ぜないことも検査する。
実行結果は[RESULTS.md](RESULTS.md)を正とする。

## 公式Protocolの調査から残ること

2026-10-28に[公式Loro Protocol](https://github.com/loro-dev/protocol)のソースを確認した。
公開パッケージは`loro-websocket@0.6.2`、`loro-adaptors@0.6.1`。
導入はまだしておらず、依存関係も増やしていない。

[SimpleServer](https://github.com/loro-dev/protocol/blob/main/packages/loro-websocket/src/server/simple-server.ts)
の`handleDocUpdate`は取り込み後にdirtyを付け、ACKを返す。
`onSaveDocument`は別の定期保存で呼ばれるため、そのACKを今回の保存確定と同じ意味には使えない。
さらに保存アダプターのsnapshotが未適用受信を含めて復元できるか、端末の自動送信を
IndexedDBの保存完了より後へ制御できるかを確認する必要がある。

[クライアント](https://github.com/loro-dev/protocol/blob/main/packages/loro-websocket/src/client/index.ts)の
公開Room APIの`waitForReachingServerVersion()`は、端末が参加時のサーバーの版へ追い付く条件であり、
端末の送信が永続ストアへ確定した条件ではない。調査したソースの`handleAck`は失敗を`onUpdateError`へ通知するが、
成功ACKを端末の保存済み操作IDへ対応させる公開callbackは確認できなかった。
別の確認プロトコルを新設して埋める前に、保存後の完了通知と未適用受信の保全を既存部品へどう接続できるかを決める。

次は、この保存確定の試験を満たす既存通信部品の接続方法を絞り、依存追加を相談したうえで置き換える。
独自のWebSocketプロトコルや認証SDKを追加実装する工程にはしない。
本体の既存認証UIのセッションとの接続、同じ利用者の複数窓、常駐サーバーとDBの運用、実機PWA、移行は引き続き残る。
