# Loroの木を小さく比較する

2026-10-26、検証パッケージ0.5.0。ユーザーの承認を受け、検証専用に
`loro-crdt@1.17.1`（MIT）だけを固定して追加した。
今回はNode.jsでLoroの実際のWASMを動かす意味の試験。
ブラウザー画面・同期サーバー・IndexedDBへ接続した第三のエンジンではない。
本体と本番の依存・コード・保存先は変更しない。

## 比較の条件

同じ30行と親子構造を一度だけ作り、そのバイナリから3つの独立したLoroDocを用意する。
アプリの行IDはメタデータへ残し、ネイティブのTreeIDと両方を照合する。
本文はLoroText、木はLoroTree。移動で本文をコピーし直したり、親IDを自作で修復したりしない。

二つの端末の相互移動は全6受信順と重複を試す。
三つの端末の循環候補、固定した16系列の合法な移動（各端末10回まで）も全6順で交換する。
3文書が一致することだけでなく、全行が通常表示または削除済みとしてアクセスでき、
循環・親不在・行IDの重複がないことを照合する。限定した試験であり数学的な証明ではない。

## 今回分かったこと

| ケース | 実測した結果 |
| --- | --- |
| AをBの下、BをAの下へ移す | 独自の循環修復なしで同じ木になり、30行が通常表示に残る |
| 三つの枝の循環候補 | 同じ条件で木を保持する |
| 同じ枝の別々の移動・兄弟の並べ替え | 子や本文を複製せず、同じ親と順序へ収束する |
| 移動をUndo/Redoし、その間に別端末が本文・属性を編集 | 別端末の編集と両方のIDを保持する |
| 削除印を付け、削除を知らない端末が子に追記し、Undo/Redo | 同じIDのまま最新の本文を表示へ戻し、再度隠せる |
| 削除した親から子を外へ移す | 子を通常表示へ残す |
| 古い未編集の文書へ最新を取り込む | ローカルの編集操作を発行しない |
| 圏外の編集をバイナリから復元して別端末と交換 | 本文と属性を両方残す |
| 同じ保存から二つの文書を作って編集 | 異なるpeerで合流し、片方のUndoで他方の追記を消さない |
| 本文の先頭と末尾への別々の追記 | 自動統合し、自分の追記だけUndoする。IMEの試験ではない |

単純な親IDのYjs案にあった循環について、Loroの専用の木は有望な結果を示した。
同じ枝の両立しない移動は一方の配置へまとまる。全行と本文が残ることを確認した段階であり、
採用されなかった移動の意図を利用者が見比べるUIまでは実装していない。
ただし次の二つは未解決または採用しない操作として区別する。

### 素のTree削除とUndoは今回の復元仕様に合わない

`tree.delete()` の後、圏外の別端末が子の本文に追記し、削除した端末へ取り込んでから
標準Undoを行うと、今回の1.17.1では枝のTreeIDと本文の入れ物が再作成される。
旧入れ物には追記が残る一方、復元されて表示される枝の本文は削除時点の写しになることを再現した。
30行の合成文書では、削除側を含むノード数が38へ増える。
保存データ全体から消えたという意味ではないが、利用者が期待する復元にはならない。

このケースも再現試験として残す。試験成功をUXの合格とは扱わない。
比較の共通仕様である「削除印だけを付ける」方式では、本文の入れ物を削除しないため、
同じIDと最新の追記を保ったUndo/Redoができた。今回の候補ではこの方式を使う。
Loro全般の削除や別のデータ配置まで同じ結果になると断定したものではない。

### 削除済みの親への古い移動は、自動では自然な表示にならない

削除印を知らない端末が、その親の下へ別の枝を移すと、合流後の枝は削除済み欄へ入る。
本文は残るが、移した側には見失ったように感じられる。木の循環防止と、削除のUXは別の問題。
Loroがアプリ独自の削除印の意味まで解決するわけではない。
同じ場所に両立しない編集があるときの、枝に限定した確認・回復の設計は残る。
全体停止やJSON書き出しを通常の回復手順にはしない。

## 保存バイナリの境界

`loroCheckpoint()` はsnapshotと、先行更新を待っている受信バイナリの両方を同期的に作る。
枝の作成より後の編集が先に届いた状態で、snapshotだけから復元すると後の編集を引き継げない。
両方から復元し、後で作成の更新を受け取れば本文まで適用できることを確認した。
待機中の更新がなくなった場合は `pending: null` とし、古い待機データを残す表現にしない。
壊れたバイナリも空の成功結果へフォールバックせず失敗させる。

今回はメモリー上のバイナリを再構築する試験。IndexedDBの永続取引、電源断、送信待ちの
確定やサーバー保存まで動かしたものではない。次の接続では、snapshotとpendingを同じ世代の
端末取引で保存し、保存失敗時に元のデータを残す必要がある。

## 実行と次の区切り

```sh
pnpm exec node --test scripts/loro-tree.test.mjs
pnpm test:unit
```

新しいLoro試験は22件。以前の21件と合わせた結果とCIは [RESULTS.md](RESULTS.md) を正とする。
コード `d92a608` の[Linuxの実行](https://github.com/yohyng/taskapp/actions/runs/40257312680)で単体43件が成功した。
ブラウザー84件は既存のYjs/PowerSyncの比較であり、Loroのブラウザー合格数に数えない。

次はこの候補を、まず30行の入力画面・端末保存・実際の更新交換へ縦に接続する。
枝ごとのCodeMirror接続、変換中の受信、持ち替え、圏外再読み込み、保存済みデータとの一致を
既存二案と同じ条件で比較する。これが通ってから1万行の全体負荷と方式の推薦へ進む。
実機PWA、認証、運用・費用、旧データ移行も本番移行前の条件として残る。

入力接続の前に公式CodeMirror接続のソースも確認した。枝ごとの本文を選ぶ関数は渡せる。
ただし複数のイベントを処理する箇所の早期returnと、Undoの単一コールバックの扱いがあるため、
次のケースを先に再現して、複数の入力欄でそのまま使えるかを判断する。
現時点ではパッケージを導入・実行した結果ではなく、ソースから試験条件を立てた段階。

- 一度の受信に木の移動・属性・二行の本文が混ざっても、両方の入力欄が更新されること。
- 複数の入力欄で一つのUndo履歴を共有しても、編集した行と選択範囲へ戻ること。
- 別の行を操作した後でも、日本語変換中の行へ受信内容が正しく届くこと。

`loroNode()` は今回の30行の試験用に全ノードを走査する。1万行の入力経路にこの探索を
毎回持ち込まず、実際の接続では行IDとネイティブIDの索引も必要になる。
