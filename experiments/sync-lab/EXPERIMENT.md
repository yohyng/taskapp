# 同期基盤の比較実験

2026-10-25。合意したUXを既存の同期基盤で実現し、独自の復旧処理を減らせるか判断する。
本番Task Spaceとは別のフォルダー・パッケージ・ポート・保存領域で試す。

## この実験で決めること

比較するのは「Yjsというアルゴリズム」と「PowerSyncという製品」の単純な優劣ではない。
同じ小さなアウトラインを動かす二つの構成について、利用者が保存・同期・復旧を意識せず
書けることと、そのために残る独自コード・サーバー運用を比較する。

| | A：文書中心 | B：DB中心 |
| --- | --- | --- |
| 端末保存 | Yjs + y-indexeddb | PowerSync Web SDKのSQLite |
| 通信・サーバー | Hocuspocus + 永続化 | PowerSync Service + 検証専用Postgres/Supabase |
| 編集 | Y.Textの文字操作、Y.Mapの属性 | PATCHと編集前の値を送るAPI |
| 同じ本文の編集 | 文字操作を統合。文章として自然かも確認 | 最初は双方を保全し、全体を停止させない |
| 今回の状態 | 小さい実装を作成、ブラウザー試験を実行 | SDK・API・Docker構成を実装。実行結果はRESULTSを参照 |

同じ本文の結果が二案で同一になることは要求しない。統合結果を見える形で比べ、
双方の意図の保全と、日常的に確認操作を求めないことを評価する。

## 第1段階の縦に通す範囲

30行、3つの独立したブラウザー保存領域、1つの本物の共有サーバー。
本文・お気に入り・完了を編集できる。初期文書はサーバーで一度だけ作る。
各端末が同じ初期JSONから別々のCRDTを作って、後で重複させる構成にはしない。

1. 端末Aで書く→端末Bで続きを書く→端末Cで続きを書く。
2. 端末Aの同期通信を切る→本文へ追記→Bでお気に入り変更→Aを再接続。
3. 同期通信を切って書く→端末保存を確認→ページを読み直す→再接続。
4. AとBを切断して同じ本文へ追加→再接続→AのUndoでBの追加を消さない。
5. 端末を読み直しただけでは、サーバーの文書変更件数を増やさない。

合格は「画面が動いた」だけにしない。3端末の全行・属性と、サーバーに保存された
バイナリを読み戻した全行・属性が一致することまで確認する。

## 最小のデータと操作の境界

共通の表示データ：

```js
{ id, parentId, order, text, favorite, completed }
```

共通の操作：

```text
snapshot() → 表示用の行
replaceText(id, value) → 通常入力の変更範囲を反映
insertText(id, index, value) → 意図を固定した文字追加の試験
setAttribute(id, key, value)
undo() / redo()
disconnect() / connect()
localBarrier() → 今行ったローカル保存の確定を試験から待つ
serverState() → サーバー側の保存内容を試験から読む
```

この境界へ現在の巨大なOutlineProviderは持ち込まない。
今の木の操作や画面をそのまま移植する前に、保存・受信が独立して成立するか確認する。
PowerSync側もこの境界を使う。本文の同時編集では結果が異なるため、両方の保全と
文字の統合を分けて評価する。PowerSync側のUndoは列の値を照合する試作で、
別端末の本文編集をまたぐUndoは未完成。Yjsのorigin指定Undoと同等とは扱わない。

## Aの具体的な構成

```text
ブラウザーA / B / C
  ├─ 小さいアウトライン画面
  ├─ Yjs（文字と属性）
  ├─ y-indexeddb（それぞれ独立した端末保存）
  └─ Hocuspocus provider
             ⇅ 本物のWebSocket
Hocuspocus Server（127.0.0.1:4181）
  └─ Database extension → .data/内の文書バイナリ

検証画面：127.0.0.1:4180
```

サーバー保存は一時ファイルの書き込み後にrenameする。試験用ファイル保存であり、
電源断まで含むfsync保証や本番DBのトランザクションを検証したとは扱わない。
サーバー確認APIはメモリーの文書ではなく、保存ファイルを新しいY.Docへ読み戻して返す。

「WebSocket接続中」「通信上の未確認なし」「サーバー保存ファイルと一致」を区別する。
providerのsyncedや未確認件数0を、サーバーへの永続保存完了という意味に使わない。

通常入力はtextareaの変更前後から一続きの変更範囲を求め、Y.Textへ反映する。
全文を毎回消して再挿入しない。ただし複雑な入力やIMEの接続が完成したとは扱わず、次の段階で検証する。

## Bで必要になる構成

PowerSyncの[公式ローカル開発手順](https://docs.powersync.com/integrations/supabase/local-development)を基準にする。
本番Supabaseの資格情報は使わない。必要な構成は次のとおり。

- 検証専用Postgres/SupabaseとPowerSync Service。
- その環境専用の認証・同期対象の定義。
- PowerSync Web SDKのローカルSQLite。
- 操作を受けるAPI。操作IDで重複を防ぎ、変更した列だけを適用する。
- 同じ本文の両立しない編集を保存する領域。未変更の属性は上書きしない。
- iPadの保存方式と複数タブを含む設定。

このPCではdockerコマンドおよび標準のDocker Desktop実行ファイルが見つからなかった。
ローカルのBを起動したとは扱わない。次の工程で、Dockerを使える検証環境を用意するか、
専用のCloud環境を使うかを決める。アカウント作成や課金・本番接続はまだしていない。
これを単純なWebSocketの自作モックで代替し、PowerSyncの検証に成功したとはしない。

## 第2段階：アウトライナー固有の意味を試す

第1段階が通ってから、次を追加する。

- 日本語IMEの変換中に他端末の追記を受け取る。絵文字、改行、貼り付け、選択範囲の置換。
- 枝の移動、字下げ・字上げ、追加、削除、Undo。親の循環や削除済み行の意図しない復活を防ぐ。
- 折りたたみは端末別の表示設定として比較し、本文の保存条件に混ぜない。
  本番で端末間共有するかは、この実験での使い心地を見て仕様として決める。
- 通信中の追加入力、送信成功後の返事喪失、サーバー再起動、通知の重複・遅延。
- 読み込み途中の空と、本当に空の文書を区別する。

文字の統合ができても、木が正しい保証にはならない。
ここで必要になる独自コードが多すぎる場合は、Automerge/Loroを含め再評価する。

## 第3段階：1万行と実機PWA

- 合成データを1万行へ増やし、初回表示・端末保存・サーバー確定・別端末表示を別々に測る。
- PC Chrome PWA、実際のiPad PWA、Android Chrome PWAで持ち替える。
- 同期通信だけでなくHTTPも切り、圏外でアプリを閉じて開き直す。
- アプリ更新・旧クライアントの復帰、認証切れ、容量不足の動作を確認する。
- 画像アップロード中に本文を変更・削除して、遅い返事が編集を戻さないことを確認する。

現在のブラウザー試験はService Workerを無効にしているため、圏外でPWAそのものを
起動できることは未確認。異なる実機の性能・入力挙動も未確認。

## 採用の判定

最優先は、入力が残ることと、持ち替え・復帰が自動で完了すること。
その条件を満たした候補を、以下で比較する。

| 項目 | 記録するもの |
| --- | --- |
| 編集の保全 | 失われた操作、意図しない復活、重複、衝突した箇所の扱い |
| 普通に使えるか | JSON退避や全体取り込みが必要になった回数 |
| 体感 | 入力→画面、入力→端末確定、入力→他端末表示の遅延 |
| 保守 | 独自の同期・復旧コード、特別な状態、必要なテスト |
| 運用 | サーバー構成、監視、バックアップ、費用とライセンス |
| 移行 | 既存ID・親子・本文・属性・未送信の引き継ぎと戻し方 |

本番データで試行錯誤しながら方式を変えない。合成データで通った後に、
読み取り専用のコピーを使って旧データの移行を検証する。
未送信の編集は本文だけ取り込んで捨てず、編集前の基準と元の記録ごと保全する。
