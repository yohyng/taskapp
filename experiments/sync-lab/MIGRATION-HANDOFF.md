# 旧端末の未送信を引き継ぐ（0.16.0）

目標は、旧端末を開いただけで新文書を巻き戻さず、その端末で行った編集を残すこと。
旧JSONにはLoroの操作履歴がないため、端末ごとにJSONから別のLoro履歴を作って統合しない。
同じ移行snapshotを全端末で共有し、旧キューから確認できる編集だけを一度引き継ぐ。
これは移行時の処理で、日常の同期は既存のLoro経路を使う。

## 今回の実装範囲

`src/legacy-outline-handoff.js`は旧checkpointと新側の木を受け取り、副作用のない候補を返す。

- 未送信キューが空なら、古い本文・色・位置が残っていても変更候補を作らない。
- 旧操作の`baseSignature`から編集前の値を読み、本文・表示属性の変更項目だけを取り出す。
- 編集前の値と最新値が同じ項目だけ候補にする。同じ結果が既にあれば追加しない。
- 別端末の色・親子・順序はそのまま残す。日時だけで競合や新しい編集と判定しない。
- 相容れない本文、基準欠損、未知の属性は旧checkpoint全体のコピーに保全する。
- 新規行は、旧キューの作成世代0・旧既知IDにないこと・新文書の削除履歴にもないことを確かめる。
  新規親を先に作り、既存行の移動が終わってから兄弟IDを目印に配置する。
- 枝の削除は、現在の子孫すべてに旧削除操作と一致する基準行がある場合だけ候補にする。
  別端末の新規子や追記がある枝は保全し、削除済みのIDも再作成しない。
- 移動は基準位置が最新と一致し、親が存在して循環しない場合だけ候補にする。
  移動する次の兄弟を未確定の目印にせず、表示順で確定した前の兄弟を優先する。

候補には変更列の`set`と、計画時の最新値`expected`を持たせる。
これを作っただけで適用済みにはしない。`settled`も値が既に一致しているという判定であり、
旧キューや送信中のflightを削除する許可ではない。元の記録は`archive`に丸ごと残す。

## 一度限りの端末保存

`src/commit-outline-handoff.js`は新文書の保存を復元して候補を作り、作業用Loro文書にだけ適用する。
生きている編集エンジンの文書を直接変更しない。候補作成時の本文・属性・位置も再検査する。
呼出元の所有者、旧保存の所有者、新側の所有者別ストレージが一致しない場合は開始しない。
呼出元が取得した`remoteHead`までの保存と、因果上の未適用差分がないことも必要。

IndexedDBの同じ取引で次を確定する。

- 原本・保留内容を含む引き継ぎ記録
- 新しいLoro差分と、その同じバイナリ・固定IDの送信待ち
- 元のcheckpointのSHA-256をキーにした処理済み印

作業中に保存世代・まとめ直し位置・末尾の差分番号・受信位置が変われば、古い候補を保存せず再検討する。
同じ控えが先に確定していれば差分を追加しない。処理済み記録の形式・所有者・原本も確認する。
取引を途中で中止すると控え・編集・送信待ち・印がすべて戻り、以前の保存から再試行できる。
再読み込み・ACK後・まとめ直し後も同じ控えを再適用しない。保留した旧内容は引き継ぎ記録に残る。
返り値の`applied`は端末のこの取引を確定したことだけを指し、サーバーへの送信完了ではない。
同じ控えを処理済みでも、保存済みの送信待ちは通常の同期経路で送り続ける。

この処理は編集エンジン開始前の排他区間用。製品の起動経路にはまだ接続していない。
旧書き込みの停止、所有者を確認した控えの一度限りの捕捉、最新head取得を行う切替処理が次に必要。
利用者が開くたびに違う原本や別のLoro履歴を作るものではない。

## PC内のリハーサル

labディレクトリで次を実行する。

```sh
node scripts/prepare-outline-handoff.mjs <旧端末のoutline書き出し.json> <新側のoutline.json> <新規出力フォルダー>
```

旧端末のJSONには`syncDiagnostic`が必要。ないものを「未送信なし」とは扱わず中止する。
通常のDrive控えはこのコマンドへの入力にしない。
最新側には`items`形式のJSONを指定する。今回の検証では移行候補の戻し用JSONを使った。
本番サーバーから最新を取得したものではなく、他端末の未送信も含む検証ではない。

出力は次の四つ。通信・本番DB更新・端末ストレージ更新は行わない。

- `source.json`：旧端末の入力をバイト列のまま保全
- `latest.json`：比較対象の入力をバイト列のまま保全
- `plan.json`：旧checkpoint全体と、項目変更・構造変更・一致・保留の候補
- `manifest.json`：二つの入力のSHA-256、候補件数、`applied: false`

既存フォルダーへの再出力は拒否する。途中失敗でも原本を変更せず、manifestを最後に書く。
私用データはgit対象外の`.data/`内だけに置き、ログには本文や画像URLを出さない。

## 次に必要な接続

候補作成と端末保存の検証は本番移行の完了ではない。次の条件を満たして起動経路へ接続する。

1. 旧保存の所有者と移行先文書を確認し、旧書き込みを止めた一貫した保存を捕捉する。
2. RPCから最新headまで保存し、排他区間で今回の処理を呼び、保存後に新エンジンを開く。
3. 取り込みを保留した原本の保持と参照、旧保存の成功後の保全を製品へ接続する。
4. Drive控え・旧版からの切替・各実機PWAで持ち替えとIMEを確認する。

移行用の確認画面や競合帯は追加していない。通常の利用者に候補ファイルの操作を要求するものでもない。
