# 日本語入力と受信の比較

2026-10-26。0.3.0で追加した入力接続。入力検証画面は `/?doc=demo&input=bound`。
PowerSync側は `&engine=powersync` を加え、READMEの実サーバー起動手順を使う。
パラメーターを省略した旧textareaは基本比較の対照用で、日本語入力の完成形ではない。

## 再現できた問題

旧textareaで、端末Aが日本語を変換している間にBが本文の先頭へ「別端末：」を追加する。
Aで変換を確定すると、全文差分を内部の最新値に当ててしまい、Bの追加が消えた。
Chromiumの `Input.imeSetComposition` / `Input.insertText` を使った試験で再現した。
単にYjsへ保存するだけでは、古い画面と新しい内部データのずれを防げない。

## 追加した入力接続

Yjs側はCodeMirror 6と `y-codemirror.next` のY.Textバインディングを使う。
入力トランザクションとY.Textの文字操作を直接つなぎ、受信を画面の全文保存へ変換しない。
既存のY.UndoManagerを渡し、入力欄のUndo/Redoでも自分の変更だけを扱う。
比較用パッケージにだけ依存を追加し、本体の依存は変更しない。

PowerSync側も同じCodeMirrorを使うが、SQLiteの値と画面の編集前本文を区別する。
通常入力には画面が見ていた本文をmetadataとして付け、APIがその値で照合する。
DBが受信済みでも、利用者が最新版を見た編集として誤って受け付けない。
同じ本文が画面の基準から変わっていれば、サーバーで両方を保全する。
この試作は先頭と末尾への共存できる追記でも別案になるため、消失しなくても確認操作が残る。
この点は、目指す「確認操作なしのUX」を満たせたとは評価しない。

変換途中の入力は端末内のlocalOnlyテーブルに毎回保存し、同期キューには入れない。
確定時に、同期対象の更新と下書き削除を同じSQLite取引にまとめる。
取り消しでは下書きだけを除き、古い本文をサーバーへ書き戻さない。
再起動で復元した未確定入力は、表示や接続だけでは送らず、次の入力で続きを保存する。

Yjs側では変換途中の文字も文書の編集として保存され、再接続時に同期される。
PowerSyncの未確定下書きと同一の扱いではない。この違いも実機で評価する。

## 試験の範囲

- 変換中の別端末の追記と、確定した日本語の保全。
- 変換中の別端末の属性変更。余計な確認を求めず両方を保存する。
- 変換取り消しで受信した追記を消さず、PowerSyncで余計な競合を作らない。
- 絵文字・複数行・選択範囲の置換と、再読み込みによる復元。
- 圏外の変換途中で開き直し、保存済みの入力から続きを書く。
- Yjs入力欄のUndo/Redoで、別端末の追記を残す。
- PowerSyncで、DBは新しく画面は古い場合の両方の保全。
- PowerSyncのlocalOnlyテーブルを実SDKで更新し、再起動後も送信待ちを作らずに残す。

Chromiumは入力プロトコルを使い、WebKitはDOMの変換イベント列を模擬する。
どちらもOSの日本語候補選択・iPadのキーボード・AndroidのEditContextを検証したものではない。
CodeMirror経由の文字入力の試験であり、本体のcontenteditableへの組み込み完了でもない。
変換全体をUndo一回で戻す単位や、長い変換・OS固有の入力操作も追加確認が必要。
枝の移動・削除、1万行、保存容量不足、サーバー再起動、本番データ移行は別の工程に残る。
