# 編集差分の端末保存と、安全なまとめ直し

0.9.0の独立したLoro経路。入力ごとの全文snapshot作成を外し、実際のLoroバイナリをIndexedDBへ追記する。
画面の回復操作や設定は増やさない。本番の保存形式・データ・Driveは変更しない。
実行した結果とコードは [RESULTS.md](RESULTS.md) に記録する。

## 保存の単位

専用DB `taskspace-lab-loro-<文書ID>` の版2に三つのストアを置く。

| ストア | 内容 | 更新する場面 |
|---|---|---|
| state | snapshot・未適用受信・世代・まとめ済みの番号 | 初回作成、旧形式の移行、まとめ直し |
| updates | 単調増加番号と受信または編集の生バイナリ | ローカル編集、内容が増える受信 |
| outbox | 一意なIDと未確認の送信バイナリ | ローカル編集で追加、実際に送ったIDのACKで削除 |

ローカル編集は差分と送信待ちを**一つの取引**へ置く。送信は、待っている間に増えた保存も含め、
追記の確定を待つ。応答は、その受信差分の追記と送信済みIDの削除を一取引で行う。
受信が空で送信もなければ書かない。接続表示を変えるだけで本文の更新を作らない。
送信待ちはsnapshotへ埋め込んで上書きせず、次の入力を前の送信完了で消さない。
応答を失った場合は同じLoro操作のバイナリを再送する。

起動はsnapshot、snapshot時点で未適用だった受信、その後のupdatesの順に戻す。
updatesには先行操作待ちの受信もそのまま残る。順序が逆でもLoroが前提の到着後に適用する。
読み取り・形式・バイナリの失敗を、空の初期データへ置き換えない。

## まとめ直しで消してよい範囲

128記録または1MiBに達すると、1秒後に保存済みの記録をまとめ直す。保存の確定を遅らせるdebounceではない。
この閾値は検証用で、端末や実データに合わせた最終調整ではない。

1. 三ストアの一貫した読み取りから、基準世代と対象の最終番号を取る。
2. その**保存済みの記録だけ**から別のLoroDocを復元し、snapshotと未適用受信を作る。
3. 基準世代が変わっていない場合だけ、新しいsnapshotと未適用受信を保存し、対象番号までのログを削除する。
   置換と削除は一取引。別のまとめ直しが先に終わっていたら、その古い候補は捨てる。
4. 対象番号より後に増えた差分は残す。outboxには触れず、途中のACKを元に戻さない。

生きている入力文書を適当な時点でexportし、後からログを全部消す処理にはしない。
まとめ直しの確定が中止されれば、旧snapshotと全ログが残る。
任意のまとめ直しの失敗だけでは入力を止めず、次の追記で再試行できる。
編集そのものの追記が失敗した場合は、従来どおり保存失敗を返し、未保存の編集を送らない。
この区別はエラーを隠して保存済みと表示することではない。

まとめ直しはメインスレッド上で別文書を復元してexportする。毎入力の処理からは外したが、
大量ログの再生やsnapshot生成の一時的な費用は残る。Worker化・電源断・OSによる保存の扱いは未検証。
初回の全更新形式が閾値未満の場合、最初のsnapshotを作る前に閉じると、再起動でもその履歴を再生する。
初回snapshot配信はこの経路の起動時の費用を含めて、次の工程で解消する対象にする。

## 旧形式からの引き継ぎ

0.8.0までの検証専用DBのsnapshot・未適用受信は、そのバイナリのままstateへ残す。
outboxだけをID付きの別ストアへ移す。送信待ちの操作は旧snapshotにも含まれるため、
JSONから再構築したり、新しいLoro操作として作り直したりしない。
スキーマ更新の取引が中止されたら、旧版1の領域と値が残る。
成功後の版2を0.8.0が開くダウングレードは対応していない。本番切替の戻し方ができたとは扱わない。
本番の11,000行超・旧同期の未送信内容からの移行は、別の工程で検証する。

## 検証する境界

- 一万行の基準から小さい編集だけを再生し、本文・親・順序・属性・ネイティブIDを保つ。
- 未適用の受信をまとめ直して再起動し、後から前提が届くと全文を復元する。
- 更新・送信待ち・ACKの追記取引が途中中止されても、旧記録を部分更新しない。
- まとめ直し中の追加入力・受信・ACKと、競合する二つのまとめ直しを実IndexedDBで試す。
- まとめ直しの取引中止、移行の途中中止、壊れた記録から空へ戻さないことを試す。
- 実エディターの圏外入力、自動のまとめ直し、圏外再読込、再接続後の三端末と保存先の一致を試す。
- 任意のまとめ直しが失敗しても入力・再試行を続けられることを試す。
- 一万行の通信試験でも三回の追記の保存量を記録し、全文の再保存へ戻っていないことを確認する。

一万行の試験では、三回の入力後に試験からまとめ直しを明示実行し、その後の圏外再起動を測る。
`persistenceBefore` / `persistenceAfter` / `persistenceCompacted` に、その前後の記録数を残す。
この圏外起動時間は、閾値に達していない実利用のログや、まだsnapshotのない初回受信の再生時間ではない。
保存量の`appendedBytes`はupdatesに追記する差分本体の合計で、outboxにも同じ本体を保持する。
IndexedDBの索引・メタデータ・物理I/Oまで含めたディスク書込み量としては扱わない。
