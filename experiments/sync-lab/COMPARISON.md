# この試作で比較する構成と残る仕事

実行結果はRESULTS.mdに記録する。以下は実装の分担であり、本番品質の順位ではない。

| 論点 | Yjs案 | PowerSync案 |
| --- | --- | --- |
| 端末のデータ | Y.DocとIndexedDB | SQLite。SDKが更新と送信待ちを記録 |
| ダウンロード | HocuspocusがYjs更新を交換 | 実Postgresの論理レプリケーションをPowerSyncが配信 |
| 書き込み先 | Hocuspocusの保存拡張→バイナリファイル | 別途作るAPI→実Postgres |
| 別の列を変更 | Y.Mapの別キー | 変更した列だけPATCHし、変更前の値と比較 |
| 同じ本文へ別々に追記 | Y.Textの文字操作を統合 | 今回は全文の値の競合を別テーブルに保全。文字統合はしない |
| 自分のUndo | originを限定したY.UndoManager | 自前の履歴と列の値の照合。別端末の本文編集をまたぐUndoは未完成 |
| 枝の移動 | 親と順番を一つの値にする。別々の枝の移動が合流すると循環し得る | 文書単位のロックと最新の木の検査をAPIへ追加。不正な移動は別案として保全 |
| 枝の削除 | 根だけに削除印を付け、子孫の本文を残す | 同じ削除仕様。古い端末から削除済みの親へ移す要求は拒否・保全 |
| 再送 | Yjs更新は重複適用しても増殖しない。応答喪失の試験は未実施 | API側の操作IDとDB取引を自作。応答喪失の試験対象 |
| サーバーの運用 | 同期サーバーと永続ストア | ソースDB、論理レプリケーション、PowerSyncの内部DB、同期サービス、書き込みAPI |
| 本番のタスクDBとの関係 | 本文を文書へ移す設計が必要 | 行の構造は近いが、既存の保存・受信経路の置き換えが必要 |

## 採用の前に必ず潰す点

0.2.1の共通textareaは比較用の簡易入力で、完成したエディター接続ではない。
画面に表示した本文と、非同期で更新された内部データが食い違う瞬間を再現する必要がある。
PowerSyncのtrackPreviousはSQLiteへの書き込み時点の値を残すため、
利用者が実際に見て編集した値との一致を、それだけで保証しない。
Yjs側のtextarea差分も、IME中に届いた編集を正しく残す保証はない。
両方式とも、ここを未検証のまま「古い内容を上書きしない設計が完成」とはしない。

0.3.0では、この入力のずれを実際に再現し、別の入力検証画面を追加した。
Yjs側はCodeMirrorとY.Textの既存バインディングへ接続する。
PowerSync側もCodeMirrorを使い、見ていた本文のmetadataと端末内の変換下書きを独自に追加した。
実行範囲とOSのIMEとの差は [INPUT.md](INPUT.md) に記録する。
実サーバーの比較では、Yjs側は変換中の先頭・末尾の追記を自動統合できた。
PowerSync側は同じケースを別案として保全し、消失を防いでも確認操作が必要になる。
本文についてはYjs案が目的に近いが、木の操作と負荷の結果を待って採用を判断する。
0.4.0では木の移動・削除を実装し、単純な親IDのYjs案に循環を再現した。
内容が失われなくても、通常表示から枝が外れて手動回復が必要ならUXの合格にはしない。
PowerSync案は最新の木をDB取引内で検査する独自APIを必要とする。
詳細と未検証範囲は [TREE.md](TREE.md)、実行結果は [RESULTS.md](RESULTS.md) を参照。
まずこの差が、日常の確認操作と独自の復旧コードをどれだけ減らせるかを判断する。

認証・端末権限、実機PWA、1万行、保存失敗とサーバー再起動、移行は両案とも残っている。
この試作のソース行数や、ブラウザー試験の件数だけでは採用しない。

## 木専用の型を持つ候補の追加

0.5.0でLoro 1.17.1を、まずNode.jsのモデル試験だけに追加した（[LORO.md](LORO.md)）。
単純な親ID方式の循環は専用の木で避けられた。共通の削除印方式では、同じIDと最新の本文を
保ったUndoもできた。一方、素のTree削除のUndoは本文を再作成して追記を表示へ戻せない
ケースを再現し、その操作は採用しない。削除済みの親へ古い端末が移す際のUXも未解決。
通信・端末保存・入力の接続を同じ条件で比較するまでは、第三の完成したエンジンとは扱わない。
