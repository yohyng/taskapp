# 採用方式を決める区切り

目指すのは、一人がPC・iPad・Androidを持ち替えて、同期の復旧作業を意識せず続きを書けること。
既存システムへの小さい修正を重ねる工程から離れ、次の三つを満たしてから方式を決める。

1. 候補の実サーバーで、持ち替え・古い端末・圏外保存・再接続・自分のUndoを比較する。
   同じ本文の競合と、保存成功の返事を失う場合は、何が残るかまで確かめる。
2. 本文入力、枝の移動・削除、Undo、1万行の負荷を試し、残る独自コードと運用を整理する。
   日本語IME中の受信を含め、アルゴリズム上の収束と使いやすい編集結果を混同しない。
3. 方式を一つ推薦し、理由・代替案を退ける理由・本番へ移す前の条件を文書に残す。

ここを最初の意思決定の区切りとする。小さい試作の成功だけで本番採用とはしない。
今回のPowerSync比較で、1の基本試験は実サーバーで成功した（詳細はRESULTS.md）。
Yjs側の応答喪失試験は残る。2と3は未完了。

0.3.0では2のうち入力接続の自動試験を追加し、旧textareaの入力消失を再現して修正した。
実サーバーを含むブラウザー52件・単体10件が成功。本文の自動統合はYjs案が目的に近い。
ただしOSの日本語候補選択・変換全体のUndo単位・実機入力は別途確認する。
0.4.0では枝の移動・削除の比較を追加した。
単純な親ID方式のYjsでは合法な操作同士が循環を生むことを再現でき、本文だけで採用を決められない。
PowerSyncの最新の木の検査・拒否・保全と比較し、[TREE.md](TREE.md) に制限を残す。
木の競合を既存の型で扱える候補も検討し、独自の回復機構が増える方向を避けてから、
1万行の全体負荷と最終的な推薦へ進む。
0.5.0ではユーザーの承認を受けてLoroを検証専用に追加した。
木・Undo・保存バイナリのモデル試験を行い、次は30行の画面・保存・通信をつなぐ。
Loroの単体試験と既存二案の実サーバー試験を混同しない。
0.6.0ではその30行の経路を接続した。日本語変換中の受信、圏外再読み込み、
送信中の追加入力、返事を失う再送、複数行と属性が混じる受信をブラウザーで比較する。
次は1万行の全体負荷と独自コード・運用の整理から、方式の推薦へ進む。
Loroの実験用HTTP交換を、そのまま製品の同期サーバーとして推薦したものではない。
0.6.0の実行では、単体45件・3方式のブラウザー142件がCIで成功した。
このうちLoroも58件のブラウザー比較を通し、30行の接続の区切りまで達した。

0.7.1では同期・保存を合成1万行で測る独立した経路を追加した（[PERFORMANCE.md](PERFORMANCE.md)）。
全行に検証用メニューを付ける画面は使わず、表示を60行に限る。
保守・運用の分担と、次の試作をLoroの文書へ絞る理由を [DIRECTION.md](DIRECTION.md) にまとめる。
これは方式選定の区切りで、本番導入の完了ではない。実際の製品画面の描画負荷も別に確認する。
当初挙げたYjsの応答喪失試験は未実施のまま。親IDの木に循環が残るため現構成は推薦せず、
この未実施は成功扱いにせず、推薦しない構成の追加検証をここでは広げない。
次は選んだLoro経路の全行変換・全文保存・初回配信を改善し、同じ保全条件で測り直す。

0.8.0では本文・属性の変更行だけを読む表示データを実装した。
単体52件・ブラウザー144件・合成一万行6件がCIで成功し、Windows WebKitの一万行試験も今回は成功した。
待ち時間と読出し行数は [PROJECTION.md](PROJECTION.md) に記録する。
表示データ更新の区切りを終え、次は端末の差分保存とまとめ直し、初回snapshot配信を別工程で進める。

0.9.0では差分保存とまとめ直しを実装する。編集差分・送信待ちの追記と、受信・ACKの確定をそれぞれ一取引に保ち、
まとめ直しは保存済みの番号と世代に限る（[PERSISTENCE.md](PERSISTENCE.md)）。
試験結果は [RESULTS.md](RESULTS.md) を正とし、次は初回snapshot配信へ進む。本番へはまだ移さない。

0.10.0では空の端末の初回をsnapshot配信へ変え、既存端末は差分交換を続ける。
前提待ちの受信を含む端末保存と、まとめ直し前の圏外起動も確認する（[BOOTSTRAP.md](BOOTSTRAP.md)）。
0.10.1では空の文書への購読とUndoの接続も受信・保存後へ移す。
結果を確認した後、既存Protocolの永続化保証・複数窓・PWAを含む製品向け経路へ進む。本番へはまだ移さない。

0.10.1の実装`8dc9b6f`で単体62件・ブラウザー168件・一万行6件がCIで成功した。
Windows WebKitの一万行3反復も全行一致し、空の端末の初回は835–925msになった。
ここで試作の表示・保存・初回取得の改善を区切る（[BOOTSTRAP.md](BOOTSTRAP.md)）。
製品向けの認証・複数窓・実機PWA・移行と戻し方の確認は、この結果と別に残る。

## 次の区切り：本番へ安全に移せること

0.12.0では本体の既存ログイン画面とSDKを検証へ読み込み、セッション更新・ログアウト・
本人の再ログイン・online復帰をつなぐ。編集画面とUndoをトークン更新から分離する。
次は既存SupabaseのDB保存と通知を使う通信案を実DBで検証する。
この区切りと残る条件は[SESSION-INTEGRATION.md](SESSION-INTEGRATION.md)。本番へは移さない。
0.12.1では保存済み本文を通信の返事より先に開く経路も追加した。
実装`ec367ca`は単体81件・ブラウザー190件・一万行6件がCIで成功した。
既存ログインからの編集・再認証・再接続の区切りとし、DBと変更通知への接続を次へ進める。

0.11.0では、このうち認証と保存確定の境界を既存HTTP経路で検査する。
本人と文書をサーバー側で検査し、再認証・Auth障害・保存途中の強制終了・保存後の返事喪失を試す。
試験の代役Authと本番ログインを区別し、公式ProtocolのACKも永続保存の完了と混同しない。
構成と次に残る接続は[AUTH-DURABILITY.md](AUTH-DURABILITY.md)。本番への切替は行わない。
実装`bd6847c`は単体72件・ブラウザー178件・一万行6件がCIで成功した。
ここで認証と保存確定の試験の土台を区切り、既存AuthGateのセッションと通信・本体画面の接続へ進む。
Authの応答を代役にした試験の成功を、本番アカウントへの接続や実機PWAの合格には置き換えない。

- PC Chrome PWA / iPad PWA / Android PWAで、休止から復帰・圏外起動・日本語入力・持ち替え。
- 保存容量不足・保存拒否・PWA更新・サーバー再起動で、下書きが残り再送できること。
- 既存11,000行超と、各端末に残った未送信内容の移行。戻せる切り替え手順。
- 画像・Driveの控え・タスクとの参照、認証・権限、費用と運用。

実機の確認を求めるのは、試作側で再現できる問題を片付けた後にまとめて行う。
日常利用のたびにJSON退避や「向こうに合わせる」を求める方式は採用しない。
