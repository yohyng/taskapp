# 新同期の控えと復元

0.18.0で画像・Drive控えと復元候補を接続し、0.19.0で検証画面からの端末復元までを接続した。
復元は現在の履歴との合流。今ある本文・未送信・原本を消して全件置換する操作は使わない。
切り戻しも新同期とデータを維持する互換版への切替とする（[切り戻し手順](ROLLBACK.md)）。
本番のアプリ・Supabase・Driveの内容・GASは今回変更していない。

## 普段の控え

検証用の実Outlinerから、既存設定の「いま控える」と自動控えを使う。
初回本文の取得前は送らない。端末の保存が確定した後、本文の基準・追記・未送信・取得位置・移行原本を
IndexedDBの一つの読み取り取引で採り、別のLoro文書へ復元してから控えを作る。
画面の木と別時点の送信待ちを混ぜず、ACKやまとめ直しの途中の姿を採らない。

控えには次を一緒に残す。

- タスクと端末設定、および読める形の現在のアウトライン。画像URL・幅も含む。
- 元の履歴を保つLoro snapshotと、先行更新を待っている受信のバイナリ。
- 同じ操作ID・同じバイナリの未送信一覧と取得位置。
- 自動切替で保全した旧原本と引き継ぎ記録。自動で合流できなかった旧内容も残す。

Driveの合言葉と検証用SDKのログインセッションは含めない。
画像ファイル自体は従来のDrive上に置き、控えには参照を残す。ファイルの複製・削除はしない。

既存の`backupProtocol: 2`に対応するGASを再利用する。圧縮・SHA-256・文字数と保存後の応答照合も従来どおり。
新しい同期履歴は全体JSONの`outlineSync`へ追加し、`store`内のアウトラインは従来GASでも読める形にする。
GASを再更新する作業は、この追加形式のためには必要ない。

自動控えは前回から24時間経ったら行い、失敗は設定内へ残して60秒後に再試行する。
同時の依頼は一つへまとめる。自動控えの失敗で入力や同期を止めず、大きな競合帯や復旧操作を追加しない。
保存読み出しや本文取得の失敗を空データの控えとして成功扱いにしない。
ログアウト・画面終了後の遅い読み出しから送信を始めず、終了後の応答で別の利用者の状態を変えない。
既にGASへの送信を始めた控え自体は取り消さず、その利用者の採取済みデータとして扱う。

## 読み戻しと候補の展開

`readLoroBackup`は指定した所有者・文書と一致する控えだけを扱う。
CRCを含むネイティブのバイナリを読み、本文・属性・親子・順序のJSONとの一致を確かめる。
未送信のID重複や未収録の操作を拒否する。画面用JSONから別の操作履歴を作り直さない。
この読み取り関数だけでは現在の端末保存やサーバーへ適用しない。

管理側で控えから確認用ファイルを展開する場合は、検証室で次を使う。

```sh
node scripts/prepare-loro-recovery.mjs <控えJSON> <新規出力フォルダー> <所有者UUID> <文書UUID>
```

原本をバイト列のまま保全し、`snapshot.bin`、必要なら`pending.bin`、固定IDの`outbox.json`、
移行原本の`archives.json`、タスク・設定の`store.json`、現在の本文の`outline.json`を作る。
最後の`manifest.json`には各ファイルのSHA-256と件数、`applied: false`を残す。
既存フォルダーへの再出力を拒否し、入力ファイルを上書きしない。通信も行わない。

この候補は切替**後**の編集と削除履歴も含む。

## 画面からの復元

検証画面の閉じた「控えからアウトラインを復元」で、同期履歴付きの全体JSONを選ぶ。
対象はアウトライン。タスク・設定は選んだ原文の中にも保全し、この操作では現在の値を使い続ける。
普段の自動同期でこの操作を求めるものではない。

1. 端末保存に失敗した未保存の入力があれば、現在の画面を閉じず復元の開始を見送る。
   保存できる状態では前の編集エンジンの保存と終了を待ち、新文書のWeb Lockを確保する。
   切替モードでは旧文書のロックも持ち、既存の停止・移行確認を済ませる。
2. 控えの所有者・文書・ネイティブ履歴・引き継ぎ原本と処理済み印の組合せを検査する。
3. 保存済み文書へ控えの履歴をimportして候補を検査する。同じ行IDの別の履歴、同じ送信IDの異なる内容、別の移行世代は拒否する。
4. 元の基準・追記を消さず、控えのsnapshotと先行待ち受信を追記する。
   控えの未送信も元の操作ID・バイナリで追加し、端末側の未送信を残す。
   取得済みの端末のcursorは維持し、空の端末だけ控えの取得位置を引き継ぐ。
5. 合流・追加の未送信・不足している移行記録・控えの原文・復元前の全保存・処理済み印を一つのIndexedDB取引で保存する。
6. 保存後に編集エンジンを開き直す。送信するのは元から未送信だった操作だけで、復元したsnapshot全体を再送しない。

復元前のgeneration・追記末尾・cursor・未送信一覧・移行記録が変わっていれば候補を拒否する。
ACKだけが進む変更も検出する。ログアウトや画面終了は保存途中の取引も中止する。
同じ原文のSHA-256に処理済み印があれば、ACK・まとめ直し・再読込後も再適用しない。
取引が中止された場合は元の保存を開き直し、復元欄へ結果を残す。本文の大きな競合帯は増やさない。

控えの原文と復元前の姿は所有者・文書別の`state/recovery:<SHA-256>`へ残し、まとめ直しでも消さない。
ここは端末内の復元記録で、通常のDrive控えへ再帰的に詰め直さない。
日常の控えは合流後のネイティブ履歴と現在の未送信、および旧同期からの移行原本を引き続き保全する。
必要なら管理側が`readRecovery(key)`から原文・復元前の保存を取り出して確認する。

## 残る区切り

②の検証画面への接続は、端末復元と互換版への往復までを区切りとする。
本番の配信先を切り替えるリハーサルと、実接続設定の切り戻し成果物の保管は③で確認する。
③で実GAS・実Supabaseを含む通し確認、最新全体CI、実Outlinerの一万行、三端末PWA・IMEをまとめて検査する。
合成GASの成功を実Driveへの保存や実機PWAの合格に置き換えない。結果は[RESULTS.md](RESULTS.md)。
