# 新同期の控えと復元候補

0.18.0。②のうち画像・Drive控えと、別文書への読み戻し・復元候補の展開までを接続した。
現在の端末保存を置換する操作と、旧同期を再開するサーバー側の切り戻しはまだ実装していない。
本番のアプリ・Supabase・Driveの内容・GASは今回変更していない。

## 普段の控え

検証用の実Outlinerから、既存設定の「いま控える」と自動控えを使う。
初回本文の取得前は送らない。端末の保存が確定した後、本文の基準・追記・未送信・取得位置・移行原本を
IndexedDBの一つの読み取り取引で採り、別のLoro文書へ復元してから控えを作る。
画面の木と別時点の送信待ちを混ぜず、ACKやまとめ直しの途中の姿を採らない。

控えには次を一緒に残す。

- タスクと端末設定、および読める形の現在のアウトライン。画像URL・幅も含む。
- 元の履歴を保つLoro snapshotと、先行更新を待っている受信のバイナリ。
- 同じ操作ID・同じバイナリの未送信一覧と取得位置。
- 自動切替で保全した旧原本と引き継ぎ記録。自動で合流できなかった旧内容も残す。

Driveの合言葉と検証用SDKのログインセッションは含めない。
画像ファイル自体は従来のDrive上に置き、控えには参照を残す。ファイルの複製・削除はしない。

既存の`backupProtocol: 2`に対応するGASを再利用する。圧縮・SHA-256・文字数と保存後の応答照合も従来どおり。
新しい同期履歴は全体JSONの`outlineSync`へ追加し、`store`内のアウトラインは従来GASでも読める形にする。
GASを再更新する作業は、この追加形式のためには必要ない。

自動控えは前回から24時間経ったら行い、失敗は設定内へ残して60秒後に再試行する。
同時の依頼は一つへまとめる。自動控えの失敗で入力や同期を止めず、大きな競合帯や復旧操作を追加しない。
保存読み出しや本文取得の失敗を空データの控えとして成功扱いにしない。
ログアウト・画面終了後の遅い読み出しから送信を始めず、終了後の応答で別の利用者の状態を変えない。
既にGASへの送信を始めた控え自体は取り消さず、その利用者の採取済みデータとして扱う。

## 読み戻しと候補の展開

`readLoroBackup`は指定した所有者・文書と一致する控えだけを扱う。
CRCを含むネイティブのバイナリを読み、本文・属性・親子・順序のJSONとの一致を確かめる。
未送信のID重複や未収録の操作を拒否する。画面用JSONから別の操作履歴を作り直さない。
返す独立した文書は検証用で、現在の端末保存やサーバーへ自動適用しない。

管理側で控えから確認用ファイルを展開する場合は、検証室で次を使う。

```sh
node scripts/prepare-loro-recovery.mjs <控えJSON> <新規出力フォルダー> <所有者UUID> <文書UUID>
```

原本をバイト列のまま保全し、`snapshot.bin`、必要なら`pending.bin`、固定IDの`outbox.json`、
移行原本の`archives.json`、タスク・設定の`store.json`、現在の本文の`outline.json`を作る。
最後の`manifest.json`には各ファイルのSHA-256と件数、`applied: false`を残す。
既存フォルダーへの再出力を拒否し、入力ファイルを上書きしない。通信も行わない。

この候補は切替**後**の編集と削除履歴も含む。
ただし、これを元に旧同期のトリガーを解除したり、旧DBへ全件上書きする手順にはしない。
古い端末の再送と、新同期で最後に確定した編集の扱いを決めた切り戻し手順が次に必要になる。
