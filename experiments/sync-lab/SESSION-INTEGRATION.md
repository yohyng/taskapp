# 既存ログインと同期の接続（0.12.1）

本体の`src/AuthGate.jsx`をそのまま使う検証画面`session.html`を追加する。
本体の`package-lock.json`で固定したSupabase SDK 2.106.2、React、既存のReactプラグインを再利用する。
新しい認証ライブラリーやログイン画面を作らない。依存の定義・lockfile・本体の版番号は変更しない。

## 今回つながる範囲

既存AuthGate → 同じSupabase SDKのセッション → 所有者別のLoro文書 → 認証付きHTTP API → 保存ファイル。
編集には前段と同じCodeMirror接続を使う。ログインの取得・更新・保存はSDKへ任せ、
アプリの接続部品は現在の利用者と文書の寿命だけを扱う。

- 初回のセッション読込みより新しいログイン・ログアウトを優先する。
- SDKの[認証通知](https://supabase.com/docs/reference/javascript/auth-onauthstatechange)では
  セッションを受け取り、通信再開を次のタスクへ送る。通知内でSDKへ再入しない。
- 401からの[セッション更新](https://supabase.com/docs/reference/javascript/auth-refreshsession)を一つにまとめる。
  更新中も同じ編集画面・Undo・フォーカスを保ち、次の入力を端末へ保存できる。
- ログアウトや利用者切替では、その場で前の文書の通信を中止し、遅い表示通知も採らない。
  別利用者の保存へ本文や未送信を引き継がない。
- 同じ本人がすぐ戻っても、前の画面の端末保存と終了を待ってから同じ保存名を読み直す。
  未送信を削除してログインし直す経路は作らない。
- `offline`で通信を休止し、`online`・画面復帰・認証更新で自動再開する。
  ただし実機PWAの休止復帰・圏外でのページ再起動は今回の試験と別に残る。
- 保存済みの文書は端末から先に開き、最初の通信は裏で進める。
  初回応答を止めても先に入力でき、その間に増えた編集も後で送る。
  空の初回は従来どおりsnapshotの取得後に購読とUndoを接続し、大量の差分通知を作り直さない。

セッションのIDは端末保存名と画面を分けるために使う。
`getSession()`の戻り値だけでサーバーの権限を許可せず、前段の所有者・文書検査を保つ。
SDKは検証専用名`taskspace-lab-auth-<文書ID>`にログインを保存する。
このSDK自身の認証保存と、アウトラインのIndexedDBに認証情報を混ぜない条件を区別する。

## 試験と本番の境界

ブラウザーでは既存のメールアドレス・パスワード画面から入り、実SDKの
`signInWithPassword`・`getSession`・`refreshSession`・`signOut`を通す。
AuthのHTTP応答だけは使い捨ての代役で、JWTも合成値。署名検証や本番Authへの接続試験ではない。
初回取得中のログアウト、通信待ちに依存しない保存済み文書の表示、更新待ち中の追加入力とUndo、別利用者への切替、
通信停止後のonline通知と確認操作なしの再送を、ChromiumとWebKitで検査する。
単体では通知と初期読込みの競争、古い更新結果、同時更新の共有、前の画面の終了待ちを検査する。
実行結果は[RESULTS.md](RESULTS.md)を正とする。

検証画面の接続設定は試験プロセスだけが渡す。環境変数や本番URLを読まず、同一オリジンの合成Authだけに接続する。
Viteでは既存AuthGateのSupabase参照だけを検証クライアントへ差し替える。
本体のAuthGate・Outlinerや本番の保存先は変更していない。本番のアウトライン画面への統合完了とは扱わない。

## 次の通信・保存の第一候補

既存SupabaseのAuth・DB・Realtimeを使い、Loroの変更バイナリを追記保存する案を次の第一候補にする。
これは今回の実装からの設計判断であり、まだ実DBで成功した結果ではない。
公式Loro Protocolの最小サーバーへ移すだけでは、[前段で確認した保存確定の条件](AUTH-DURABILITY.md)を満たさない。
その不足を独自のWebSocketプロトコルやログインの追加で埋める前に、既存の運用先を再利用する経路を試す。

DBの[行単位の権限](https://supabase.com/docs/guides/database/postgres/row-level-security)で本人と文書を分け、
[DB関数](https://supabase.com/docs/guides/database/functions)で更新IDの重複排除と差分の追記を一取引へまとめる。
古い本文と新しい本文を行ごと比較する旧方式へは戻さず、統合は同じLoroの履歴に任せる。
[Postgres Changes](https://supabase.com/docs/guides/realtime/postgres-changes)は変更の通知に使う。
通知そのものを保存完了や完全な履歴とせず、届いたらDBの保存済みの続きから取得する。
再接続時も保存済みの位置から取り直し、通知を失っても追い付ける構成を試す。

次の区切りで確認する条件は以下。

1. 所有者別・文書別の新しい検証用テーブルとRPCだけを使い、本番の旧行を変更しない。
2. 保存した更新IDだけを返し、応答喪失の再送でも同じIDと同じ内容なら一度だけ保存する。
3. 文書の採番と追記を直列化し、後で確定した小さい番号を取得位置より前に取り残さない。
   [Postgresの行ロック](https://www.postgresql.org/docs/current/explicit-locking.html)の利用を検査する。
4. 端末の取得位置と受信差分・送信完了を同じ取引で記録し、前提待ちの受信も保つ。
5. snapshotとその確定範囲を一体にし、まとめ直し中の更新を欠かさない。
6. 送受信の小分け、payload検査・破損の扱い、通知喪失、権限拒否、DB再起動を確認する。

ここまで通してから製品の通信経路を決める。実機PWA、同じ本人の複数窓、
既存一万行超・各端末の未送信・画像参照の移行と戻し方は、その後に続ける。
