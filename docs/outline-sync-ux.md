# アウトライン同期の受け入れ条件

2026-10-22にユーザーと合意。ひとりがPC・iPad・AndroidのPWAを順番に使う。
保存や同期の操作を意識せず、端末を持ち替えて続きを書けることを目的にする。
ユーザーは裏側を意識せず開いて書けることを優先する。再接続・再送・通常の取り込みは自動で処理する。

| 場面 | 期待する動作 |
| --- | --- |
| 端末を開く | 最新を取り込む。開いただけでは書き戻さない |
| 編集する | 即座に端末保存し、その編集だけを送る |
| 別端末へ持ち替える | 自動で最新の続きを表示する |
| 圏外で編集する | 編集を残し、再接続時に最新へ重ねる |
| 同じ箇所に両立できない変更がある | 両方を保全し、そのときだけ確認する |

## 実装の判断基準

- 画面の応答を通信完了待ちにしない。入力後の端末保存を開始し、その確定後に通信する。
- 起動、サーバー受信、再接続、手動の最新取り込みは編集操作を生成しない。
- ユーザー操作を未送信キューの根拠にする。画面の木とサーバーの表現差だけで編集を作らない。
- 古い端末の未編集部分はサーバーを採る。未送信部分は保持し、編集前の状態との比較から安全に適用できる範囲を決める。
- 同じ操作の再送は同じ内容と操作IDで行う。再送途中の追加編集は別操作にする。
- 実際に競合したIDと判定経路を内部で記録する。すべての失敗を「別の端末に新しい変更があります」でまとめない。
- 本文の退避、JSON書き出し、端末を閉じる操作を日常の同期手順にしない。

## 現状監査で確認できた問題

基準コミット: e92c20d（v1.15.20）。以下はコード上の事実であり、今回の実端末の
競合IDを特定したという意味ではない。添付Driveファイルは `{}` で診断できなかった。

1. `OutlineProvider` の送信処理は未送信キューに加えて同期済み署名との差分から送信対象を作り、
   キューに無い行も `missing` として未送信化する。受信・表示変換とユーザー編集が送信判定で混ざる。
2. `mergeOutline` は未送信でない行も端末時計で選ぶ。古い端末を開く際のサーバー優先が明確でない。
3. 本文取得は1000件ずつ分割するが、`loadOutlineRevisions` の集合返却RPCには分割取得がない。
   サーバーの返却上限により本文と世代一覧の範囲が異なり得る。実端末の欠落数は未確認。
4. `buildTree` から `flattenTree` を通ると兄弟の並び番号が0始まりに詰め直される。
   送信前の比較は取得した行をそのまま署名化するため、表示側の基準と表現が異なる。
   人工データで並び番号 `[1,2]` が `[0,1]` になり、比較不一致となることを再現済み。
5. `syncNote` 自体は端末チェックポイントに保存されない。「古い警告が保存から復元された」
   という以前の説明は誤り。サーバー履歴に新しい拒否が無くても、端末内比較や同じ操作IDの
   再送による過去の拒否結果は表示され得る。

## 再現してから変更する順序

1. 良かった時点（v1.15.12付近）と現行の動作を、同じ試験条件で比較する。
2. 通信モックにも1000件の返却上限、疎な並び番号、任意列や時刻の実際の表記を反映する。
   同じ形の行を返すだけのモックで本番動作を保証しない。
3. 1万行超での未編集起動・再読み込み・手動取り込みの通信件数を測り、書き込み0を検証する。
4. 1行の本文編集では対象行だけ送信されること、表示上の正規化で他行を送らないことを検証する。
5. 2端末の持ち替え、圏外編集の再接続、互いに無関係な編集、同じ箇所の競合を検証する。
6. 本番配信版で拒否された操作IDを持つキューと、世代0の旧キューの再起動を検証する。
   操作IDを残したまま要求内容を変える修復は行わない。
7. 上記の再現結果から必要な変更を選ぶ。形式v2への移行やstart廃止を先に決めない。

## 本番反映の条件

純粋関数の試験、DB境界の試験、Chromium・WebKitの画面試験が同じ受け入れ条件を満たすこと。
修正前に落ち、修正後に通る再現試験を用意する。変更と検証結果をまとめてレビュー可能にし、
小さな推測修正の連続配信を止める。DB内の既存行・端末の未送信操作を無条件で捨てない。
直接保存を拒否する最終SQLは、引き続き未適用とする。
