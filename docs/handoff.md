## 追記（v1.15.8：本文と送信待ちを一緒に残す）

- `taskspace-outline-v1` の保存値を `format: "taskspace-outline/1"` の記録へ移す。本文の木、未送信の行と世代、削除の印、knownを同じ1件に含める。localStorageの1回のsetItem、IndexedDBの1回の確定でまとまった姿を残す。
- 旧配列と旧IndexedDB形式も読み、切り替える前に `taskspace-outline-v1-legacy-copy` へ本文と印・覚えの控えを残す。旧形式の別保存の印は削除せず、移行後の正本には使わない。控えを残せなければ切り替えを止める。書き込みに失敗しても前の保存済みの写しは残し、IndexedDBへの確定後にだけ古い小さい写しを外す。移行元と同じ写しが残っても、新形式の確定済みの本文を巻き戻さない。
- 2つの新形式の控えは保存世代で比較する。IndexedDBを読み出せない起動では、localStorageが有効でもより新しい世代の有無が分からないので保存と同期を止める。読める写しは表示し、書きかけは書き出してから開き直す。件数や端末時計で選ばない。将来の形式や不整合な未送信記録を空として書き換えず、保存と同期を止めて書き出しへつなげる。
- 手元の操作は行ごとの世代を未送信にする。端末への確定を待ってから送信し、完了した世代だけ除く。送信中の再編集・削除・取り消しは別の世代として残る。返事を受け取る前に閉じても、開き直して最新の未送信分を送る。
- 起動時の読み直しとRealtimeでは、送信待ちの行を受信で消さない。その行は手元の内容を送ってから通常の受信へ戻る。読み込み中に入力した分も、最後の読み出し後に拾い直す。
- ドライブの控えにも本文と未送信記録を含める。保存済みの本体を安全に確認できない間は控えを作らない。
- 今回も本文の全体JSON化・全体保存は残る。未送信は行単位の最新状態へまとめる方式で、サーバーの操作ID・版確認・競合する相手の本文の退避は未導入。同じブラウザの複数タブの制御と、旧版へ戻す互換性も今後の段階。旧版のタブを閉じてから新しい版へ切り替える。
- 行ごとの差分保存は次の変更に分ける。新IndexedDB／サーバーの同期プロトコルを導入した扱いにはしない。

## 追記（v1.15.7：移動と削除待ちを古い受信から守る）

- 手元の構造変更は `prepareOutlineChange` を通す。親・並び順が変わった既存行と、移動で開いた親の更新時刻を進める。移動先だけでなく、番号がずれた周囲の行も対象。同じミリ秒の連続操作でも前より新しくする。
- 通常編集・取り消し・やり直しで共通の準備を使う。文字だけの編集は共有された枝で変化を判定し、前段で減らした行オブジェクトの複製を増やさない。
- 削除した行と子孫の印は操作時点で記録し、送信までの待機・送信中・失敗後の再試行中も保つ。復元した行はその場で印を外す。
- Realtimeの250ms待機箱は反映する時点で削除の印を照合する。削除前に箱へ入った更新や、新規行の送信中に届いた古い通知から戻さない。遮断した更新を同期済みとは記録しない。
- 同期済みの記録にまだ無い行でも、削除の印があれば送信対象へ含める。起動中の操作と保存済みの印を合わせ、保存された削除待ちは再起動後も送る。
- 単体テストでTab／Shift+Tab・上下移動・ドラッグ・複数行の移動、古い行の再受信と参照共有を確認。Chromium／WebKitで待機箱、通信待ち、失敗／再試行、取り消し／やり直し、再起動、子孫を含む削除を確認する。
- 今回の保護は送信完了前の削除が対象。サーバー側の版管理・削除履歴、本体と印の一括保存、永続的な未送信キュー、他端末の編集を巻き戻さない取り消しは今後の段階。

## 追記（v1.15.6：入力時に全行を複製しない）

- `updateNode` は対象の行とそこから根までの親だけを作り直す。文字・印・見た目の編集や、ズーム中の子の入れ替えに適用する。
- 変わらない兄弟・子孫は同じオブジェクトを使う。取り消し履歴でも過去の枝を共有でき、1打鍵ごとの全行複製を避ける。
- 元の木は変更しない。更新時刻を進めるのも対象の行だけ。対象が無ければ元の配列を返す。
- 1万行・深さ3段の木では、1行の編集で新しくなる行オブジェクトを1万個から3個へ減らす。凍結した木・履歴と後続の移動／削除もテストする。
- 差分保存へ向けた準備段階。保存時の全体JSON化・IndexedDBへの全体保存・行を探す走査は残る。永続的な未送信キューや保存形式の移行は、まだ行っていない。

## 追記（v1.15.5：端末保存の失敗を知らせて再試行する）

- アウトライン本体の端末保存を、localStorageとIndexedDBの結果で確認する。どちらにも残せなかったら、画面に警告を出す。
- localStorageに入らない場合の「保存しました」は、IndexedDBへの確定後にだけ表示する。片方に残せた場合は、両方失敗と同じ警告を出さない。
- 警告から手動で保存し直せる。失敗後は15秒後にも再試行し、書き出しボタンから画面の最新の内容をJSONへ退避できる。再保存が確定するまで警告を残す。
- IndexedDBへ同時に書くアウトライン本体は1件だけ。待機中の木は最新の1件にまとめ、古い完了通知で新しい内容を保存済みにしない。
- 端末保存の結果はSupabaseのエラーと分け、互いの知らせを消さない。起動時の保存も同じ確認を通す。Providerを閉じたあとの再試行タイマーは片付ける。
- Chromium／WebKitで、片方だけの失敗、両方の失敗と復旧、書き出し、手動／自動の再試行、起動時の失敗、古い返事と新しい編集、同期エラーとの併存を確認する。
- 起動時にIndexedDBを読めず、有効なlocalStorageの写しも無ければ、本体への保存と同期を始めない。書きかけはJSONへ退避し、画面を開き直して復旧する。読み出しの失敗を「空」と扱って再保存しない。
- 今回の判定はアウトライン本体が対象。消した印・同期済みの覚えとの一括保存、永続的な未送信キュー、行ごとの差分保存は、まだ導入していない。

## 追記（v1.15.4：IndexedDBの確定まで待つ）

- `bigPut`／`bigDelete` は要求の成功時点ではなく、取引全体の `complete` 後に成功を返す。`bigGet` も同じタイミングで値を返す。
- 要求が成功しても、そのあと取引が中断されたら失敗として返す。要求のエラーや、複製できない値による同期例外も、取引の中断まで待って接続を閉じる。
- Chromium／WebKitの実際のIndexedDBで、保存・読み出し・削除の確定と中断、要求エラー、同期例外、失敗後の次の保存を確認するテストを追加。
- APIの返り値（読み出し失敗は `undefined`、保存・削除失敗は `false`）は変更しない。
- 今回は保存ヘルパーの成功判定まで。呼び出し元が `false` を画面へ伝える処理や、未送信キューの永続化は、まだ追加していない。

## 追記（v1.15.3：送信を1件ずつ進める）

- アウトラインの通常保存は、同じProviderから同時に送らない。送信中の追加編集・削除は、完了後に最新の木から差分を拾って続ける。
- 同期済みの記録に使うのは送った時点の行だけ。送信中に打った内容まで同期済みにしない。
- エラーの返事と例外を同じ再試行経路に乗せ、失敗しても送信中の状態を解除する。Providerを閉じたあとの再試行タイマーも片付ける。
- 同じ行の連続編集、別行の編集、新規行の送信中の削除、2種類の失敗からの再試行を通信待ちで再現するテストを追加。
- この段階は1つのProviderの通常送信が対象。複数タブの送信制御、永続的な未送信キュー、サーバーの版管理は次の段階。

## 3. 残っている問題

### (a) 1打鍵ごとに木を丸ごと保存している — いちばん効く改善
`src/Outliner.jsx` の保存 effect が `nodes` の変化ごとに走り、約3.2MB の
`JSON.stringify` と localStorage／IndexedDB 書き込みをしている。
PC では分かりにくいが、iPad では入力のもたつきとして出るはず。
- 対処1（小・効果大）：手元への保存も 500ms〜1秒まとめる。閉じるときに書き切る保険を付ける
- 対処2（中）：丸ごとではなく、変わった行だけ IndexedDB に書く形へ

### (b) 同じ行を2端末で同時に打つと後勝ち
行単位の last-write-wins。文字単位で融合するなら CRDT（Yjs など）が要る。
いまの用途（端末を行き来して書く）なら実用上の問題は小さい、と判断して見送っている。

### (c) ユーザーの Supabase で SQL を流したかが未確認
これを流していないと、日付・画像の幅が端末間で揃わず、Realtime も効かない。
```sql
alter table outline_nodes add column if not exists date text;
alter table outline_nodes add column if not exists image_width integer;
alter table outline_nodes replica identity full;
alter publication supabase_realtime add table outline_nodes;
```

### (d) GAS が古いままだと、控えが空になる
v1.14.2 で gzip して送るようにしたので、`Utilities.ungzip` を持たない古い GAS だと
中身の無い .json が置かれる。**デプロイを管理 → 鉛筆 → 新バージョン**で貼り直しが要る。

### (e) 取り外す約束のもの
⚙ の「アウトラインをぜんぶ消す」は、データ整理のための一時的な口（コメントに「いまだけ」）。
`src/Outliner.jsx` の該当ブロックと `tests/outliner.spec.js` の「ぜんぶ消す」describe を、
用が済んだら一緒に消す。

### (f) 散らかっているもの
- `src/App.jsx` が約9,200行。切るなら「描画だけの部品」から
- eslint のハードエラーが13件（既存ぶん。新しく足さないこと）

## 5. 判断の背景（なぜそうしたか・何を避けたか）

- **手元の置き場：localStorage を本物とし、入らないときだけ IndexedDB。**
  最初は「新しいほうを時刻で選ぶ」にしたが、書き込みの失敗や外から入れた値で
  時刻が噛み合わず取り違える事故が起きた。
  いまは「写しが残っていればそれが本物、入らなかったときは消すので、不在が合図」という単純な規則にしてある。
- **消した行の扱いは、印（tombstone）＋確かめた覚え（known）の二段。**
  印だけだと、消していない端末が古い行を送り返して復活する。
  覚えがあって向こうから消えていれば「ほかで消された」と判断できる。
- **Realtime は行の差分を当てる方式。** 変化のたびに全件読み直すのは1万行では重い。
  ただし受け取りを取りこぼしても困らないよう、60秒ごとの読み直しを保険に置いている。
- **CRDT は入れていない。** ひとりで端末を行き来する使い方に対して、
  構造と依存が重すぎる。行単位の後勝ちで足りると判断した。
- **控えは gzip。** Safari が数 MB の POST を落とす（「Load failed」）。
  分割送信も考えたが、GAS 側の組み立てが増えるので、まず圧縮で足りるとした。
- **画像は Supabase に入れない。** 無料枠がすぐ埋まる。ドライブは 5TB あるので、
  実体はドライブ、行には URL だけ。
- **取り込みは「2回読んでも増えない」が絶対条件。** id があるものは id、無いものは文字で重ねる。
  ここが雑だと、1万行が一度の操作で倍になる。
- **テストは `data-*` で掴む。** クラス名で掴んだテストが、レイアウト変更のたびに
  まとめて落ちた（実際に起きた）。
- **Playwright は同時に2つ走らせない。** preview（4173）を共有するので、
  無関係なテストが落ちて原因を見失う（これも実際に何度か踏んだ）。
