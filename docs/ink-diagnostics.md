# 手書きの遅れを測る（計測ページ）

2026-11-12 の引き継ぎで最重要とされた「Galaxy Z Fold5 + S Pen + Chrome PWA で、
手書き中にときどき線が遅れて一気に描画される」を、推測ではなく数で切り分けるための道具。

本番の配信物には入れない。Preview でだけ `/ink-diag.html` として出る。

## 何を測るか

| 項目 | 見方 |
|---|---|
| 入力の間隔（pointermove） | 50ms 超が多ければ、イベントそのものが届いていない |
| まとめ届き（coalesced） | S Pen が1イベントに何点まとめているか。多いほど端末側で詰まっている |
| 画面の更新間隔（フレーム） | 50ms 超が多ければ、main thread が塞がっている |
| 1回の描き直し | `live-sketch` が1フレームで使った時間。16ms 超が出れば描画が重い |
| 確定：文字列にする／端末へ書く／画面の更新 | 線を離した瞬間の詰まり。3つを別々に測る |
| longtask | 50ms 以上 main thread を塞いだ仕事の回数と最大 |

線の座標も本文も記録しない。残るのは時間の数だけ。

## 使い方（実機）

1. Preview の `/ink-diag.html` を開く（この計測ブランチの Vercel Preview に含まれる）
2. 画面上の「描画」「保存」を選ぶ
   - 描画：**本番と同じ** / **入力だけ（描かない）**
   - 保存：**しない** / **本番と同じ**（`JSON.stringify` → localStorage → React 更新）
3. 「記録をはじめる」を押し、画面の手順どおりに 20〜30 秒書く
   ゆっくり直線 → 速い直線 → 続けて波線 → 文字 → 長いストローク
4. 「記録をとめる」。数が画面に出る
5. 「結果を写す」か「結果を保存（JSON）」で持ち出す

## 切り分けの読み方

同じペン・同じ書き方で、設定を変えて2回ずつ測る。

- **「描画：入力だけ」にすると遅れが消える** → ライブ描画が重い。
  `live-sketch.js` は毎フレーム、現在のストローク全体（`sketchPreviewStroke` で最大512点）を
  `perfect-freehand` に通し直している。増分化が要る。
- **「保存：しない」にすると遅れが消える** → 確定時の保存が重い。
  本番は線を離すたびに全ストロークを `JSON.stringify` して localStorage へ同期的に書き、
  さらに React を更新する。非同期化・差分化が要る。
- **どちらでも遅れる／入力の間隔そのものが開いている** → 入力が届いていない。
  端末・ブラウザー側（S Pen のサンプリング、PWA の合成、他タブ）を疑う。

## すでに分かっていること（PC・headless Chromium）

| 条件 | 1回の描き直し | 確定：文字列 | 確定：localStorage | 確定：React |
|---|---|---|---|---|
| 600点の長いストローク1本 | 中央 0.3ms / 最大 3.0ms | — | — | — |
| 40点 × 24本（保存あり、下書き 32KB） | 中央 0.1ms / 最大 3.7ms | 中央 0.2ms | 中央 0.1ms | 中央 0.4ms |

**PC では再現しない。** だから実機の数が要る。
なお、この計測ページの「確定：画面の更新」は小さな表示だけを更新している。
本番は `App.jsx` 全体が描き直されるので、実機では本番のほうが大きく出るはず。
そこが効いているなら、計測ページの数より本番の体感のほうが悪い、という形で現れる。

## 開発側の使い方

```bash
npm run build:ink-diag     # 本体＋計測ページを作る
npm run test:ink-diag      # 計測ページ自体の試験（5件）
```

計測のための口は `src/lib/live-sketch.js` の `createLiveSketch(canvas, onPaint)` だけ。
`onPaint` を渡さなければ、本番の動きは従来どおり変わらない。

## 実機で分かったこと（2026-11-12 / Galaxy Z Fold5・Chrome 157）

計測ページでは **まったく再現しなかった**。

| 項目 | 結果 |
|---|---|
| 入力の間隔 | p50 8.3ms / 最大 9.8ms、50ms超 0回（120Hz で途切れなし） |
| まとめ届き | 平均 3.9点／イベント（実質 約480Hz） |
| フレーム間隔 | p50 8.5ms / 最大 22.1ms、50ms超 0回 |
| 1回の描き直し | p50 0.2ms / 最大 1.3ms（1本 1,549点でも軽い） |
| 確定（文字列・保存・React） | 0.7 / 0.7 / 0.5ms |
| longtask | 0回 |

つまり引き継ぎメモの疑い3つ（入力の詰まり・ライブ描画・確定時の保存）は、
**単体ではいずれもシロ**。遅れは手書きの道そのものではなく、その周りで起きている。
利用者の感触も「本体側」で、書きながらのスクロール（紙の自動拡張）は心当たりなし。

## 止まりの計測（本番と同じ画面で）

そこで、本番と同じ画面のまま「止まった瞬間に動いていた関数」を名指しで記録する。
Chrome の Long Animation Frame を使うので、手書きの処理には一切触らない。

検証ビルドの URL に `?probe=1` を付けると、右下に小窓が出る。
「はじめる」→ いつもどおり 30 秒ほど書く →「とめる」→「結果を写す」。

出てくるのは、フレームの間隔（50ms 超の回数）、長かったフレームの数と時間、
longtask、そして **止めた時間が長い順の犯人一覧**（呼び出し元・関数名・ファイル・合計 ms）。
上から順に直せばよい、という形で出る。

通常の配信物には入らない（`import.meta.env.MODE === "ink-diag"` の検証ビルドだけ）。

## 次の手（測ったあと）

1. ライブ描画の増分化 … 直近の点だけを描き足し、ストローク全体の再計算をやめる
2. 保存の非同期化 … 確定時の `JSON.stringify` と localStorage を、描画の後ろへ回す
3. 入力と React 状態の分離 … 線を描いている間は React を更新しない

ペンの書き味の定数（`INK_EXTREME_RETURN` など）は、遅れの対策として触らない。
保存済みの線の形が変わる。
