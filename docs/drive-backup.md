# 検証付きDriveバックアップ（v1.15.26、未配信）

端末の本文・未送信の編集・削除・タスク・設定をまとめて残す。画像の実体は以前と同じ
Drive上のファイルを使い、控えにはURLを残す。

## 確認できたこと

2026-10-23、接続されたDriveのbackupsフォルダで、直近5件のJSONが2バイトであることを
メタデータから確認した。10月21日以前にはサイズのある控えも残るが、内容の読み取り用の
ファイル参照をこの環境では解決できず、アウトラインまで揃うかは未確認。既存ファイルは操作していない。

GASの旧ソースは本文欠落時に `{}` を保存し、検証前に古い控えを整理していた。
実際のGASソースをNodeのVMで動かす試験で、変更前に不正な本文を保存・整理することを再現した。
VM内のDrive・Utilitiesは試験用の代替であり、Googleの本番サービスで実行した試験ではない。

## 保存と成功判定

- 端末データの読み出しに失敗した場合は、部分的な控えを返さず中止する。
- IndexedDBだけにある大きい本文も、画面の本文と送信記録を同じチェックポイントへまとめる。
- アプリはGETで `backupProtocol: 2` を確認してから本文をPOSTする。未対応のGASには送らない。
- 本文を圧縮できる場合はgzip、できない場合はJSONで送り、元の長さとSHA-256を添える。
- GASはJSON・アウトラインの有無・指定された長さと内容を検証してからファイルを作る。
- 保存後に実ファイルを読み直し、元の本文と一致した場合だけ古い控えを整理し、照合結果を返す。
- アプリは成功フラグ・ファイルID・長さ・SHA-256が揃った場合だけ前回の成功時刻を更新する。
- `bytes` は旧クライアントとの互換のため、従来のUTF-16文字数を維持する。

古いアプリが送る、期待するSHA-256を含まない正常な控えも、新しいGASは検証して保存できる。
全体バックアップの復元画面は追加していない。試験では別の環境に保存内容を読み戻し、
通常の起動経路で本文・未送信・削除・タスク・設定が残ることを確認する。

## 既存GASの更新

1. 画像・バックアップ用の既存Apps Scriptプロジェクトを開く。
2. `docs/gas-image-upload.gs` を使い、先頭の `FOLDER_ID` と `TOKEN` は現在の値を保つ。
3. コードを保存し、デプロイ → デプロイを管理 → 使用中のデプロイを編集する。
4. 新しいバージョンへ切り替えてデプロイする。同じデプロイを更新し、既存の `/exec` URLを保つ。
5. GAS更新後にアプリの「いま控える」を1回実行し、新しいDriveファイルの中身を確認する。

既存デプロイを新しい版へ向けるとURLを維持できることは
[Googleの公式手順](https://developers.google.com/apps-script/concepts/deployments#edit_a_versioned_deployment)に記載されている。
コードの保存だけでは既存の公開版は更新されない。

GAS側の本番更新と、更新後の実ファイルの内容確認を完了するまでは、バックアップ復旧完了とは扱わない。
アプリ側v1.15.26は未対応のGASへの送信を止めるため、先にGASを更新すると切り替えが滑らかになる。
