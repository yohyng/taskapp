# アウトラインの古い端末保護（v1.15.13、サーバー境界）

個人が複数端末を行き来する使い方では、同時共同編集よりも、久しぶりに開いた端末が
新しい本文を押しのけないことを優先する。`docs/sql/outline-cas-v1.sql` はそのための
条件付き保存（CAS）と操作IDによる再送の重複排除を用意する。

クライアントは本文と `taskspace_outline_heads()` の世代を読み、変更ごとに読んだ世代を
`expected_revision` として送る。現在の世代と一致しない変更が1件でもあれば、同じ操作の
本文は一切変更せず `conflicts` を返す。端末時計の新旧では判定しない。

同じ `operation_id` と同じ内容を再送した場合は最初の結果を返す。通信が切れて返事だけを
失っても、同じ変更を二重に適用しない。別内容で同じIDを使った場合は拒否する。

v1.15.14ではクライアントの永続キューへ世代と操作IDを接続する。入力は従来どおり先に
画面と端末へ反映し、送信時だけCAS RPCを使う。RPC未導入なら従来保存へ戻るが、導入済みの
通信失敗では直接保存へ抜けない。返事を失った再送では保存済みの操作IDを使う。

既存クライアントを壊さないため、`outline_nodes` への従来の直接保存はまだ止めない。
本番へは履歴SQL、CAS SQL、対応クライアント、直接保存の停止の順で移行する。CASに対応して
いない古いPWAが残る間は、サーバー境界の保護が完成した扱いにしない。

## 直接保存の停止

`docs/sql/outline-cas-enforce-v1.sql` は、`authenticated`／`anon`から
`outline_nodes`へ届く直接の追加・更新・削除を拒否する。CAS RPCは検証後の書き込み中だけ
取引内の印を立て、終了前に消す。DB管理者によるSQL Editorや移行作業は従来どおり通り、
履歴トリガーにも記録される。

このSQLは対応クライアントを配信し、3台のPWAを開き直したあとに適用する。先に適用すると
古いPWAは同期エラーになるが、本文を壊すことはない。緊急時は書き込みを止めてから
`docs/sql/outline-cas-unenforce-v1.sql` を実行すると、本文・履歴を消さず直接保存の拒否だけを外せる。

最終的な導入順は次のとおり。

1. 端末3台と `outline_nodes` の控えを取る
2. `outline-history-v1.sql` を適用する
3. `outline-cas-v1.sql` を適用する
4. v1.15.15を配信し、全PWAを閉じて開き直す
5. 3台からCAS保存できることを確かめる
6. `outline-cas-enforce-v1.sql` を適用する
7. 古い直接保存が拒否され、最新版のCAS保存が通ることを確かめる

競合時はクライアントの未送信記録を消さず、設定内からJSONへ書き出せる。ユーザーが控えを
取ったあと「向こうに合わせる」を選ぶと、本文とサーバー世代を一緒に読み直す。通常の編集は
これまでどおり手元へ即時反映し、競合がない送信の体感は変えない。

## v1.15.24の旧操作引き継ぎ（未配信・SQL未適用）

旧版は操作IDを残しても、送った要求一式を保存していなかった。同じIDで現在の本文を
再送すると要求ハッシュが一致しない場合があり、過去の拒否結果も同じIDでは変わらない。
元の要求を推測して送ったり、単にIDを外して送ったりしない。

`docs/sql/outline-recovery-v1.sql` は本人の旧操作の確定結果を返す。未着のIDには失効印を
記録し、元のCAS要求が遅れて届いても適用されないようにする。CASと同じ取引ロックを使い、
先にCASが届いた場合はその成功・拒否結果を変更せず返す。本文・世代・履歴には触れない。
失効印は再送の記録なので削除しない。本人以外の操作と未ログインの呼び出しは拒否する。

クライアントは確定結果を得てから本文を読み、その前後の世代が一致することを確かめる。
目的と同じ本文が届いている、または行が既に削除されている場合は、追加保存せず完了する。
編集前の本文・世代が変わっていない場合だけ新しいIDへ引き継ぐ。旧版の位置変更が分からない
既存行や両立できない本文は、サーバーと手元を残して確認する。確認中にも入力でき、古い
確認結果で追加入力を消さない。新経路の `sync.flight` がある場合は、従来どおり元の要求を再送する。

導入時は、既存の履歴・CAS SQLを入れた環境へ `outline-recovery-v1.sql` を先に適用し、
その後にv1.15.24以降を配信する。SQLが未導入・通信失敗の場合は旧操作を残して再確認し、
直接保存へ戻ったり、旧IDで推測した要求を送ったりしない。未送信の旧操作を持たない端末は
このRPCを呼ばず、通常の編集・リアルタイム受信を続ける。

この段階では本番へのSQL適用・配信は行わない。直接保存を止める最終SQLも別の導入判断とする。
