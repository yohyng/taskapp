# アウトラインのサーバー変更履歴（v1.15.12、適用候補）

別端末の編集が後から届くと、現在のupsertは前の本文を上書きする。
まず変更前後の本文と削除の履歴、端末時刻に依存しない行の世代を残す。
この段階では古い送信を拒否せず、ブラウザーからの競合表示・復元も実装しない。

SQLは `docs/sql/outline-history-v1.sql`。本番へ自動実行する仕組みは追加しない。
フロントエンドの送受信・ローカル保存形式・認証方式は変更しない。
本番はv1.15.11のまま、このPRのマージとSQL適用は別に扱う。

## 記録する内容

公開中の `public.outline_nodes` の列は変更しない。既存行も書き換えない。
同じDBの非公開スキーマ `taskspace_outline_sync` に次の表を追加する。

| 表 | 内容 |
| --- | --- |
| installation | 記録の形式、元のテーブルのOID、導入時刻 |
| heads | idごとの最新世代、削除状態、本文の写し、サーバー時刻、実行者 |
| events | 変更順のseq、idと世代、操作、変更前後の行、サーバー時刻、実行者 |

適用前からある行は世代1のbaselineとして控える。これは過去の編集履歴ではない。
新規のidは世代1から進み、削除・同じidの復元でも世代を巻き戻さない。
行の全列をJSON化するので、日付・色・画像などを列の列挙漏れで落とさない。
更新とupsertで行の内容が全く同じなら、世代・履歴を増やさない。
時刻だけが変わった場合は変更として残す。操作IDによる厳密な重複排除は次の段階。

本文と変更記録は同じ取引で確定する。記録できなければ本文の変更も取り消す。
通常のDELETEでは削除前の本文を残す。TRUNCATEは履歴を飛ばすため明示的に拒否する。
既存のアプリの全件削除はDELETEを使うので、従来のAPIを維持する。
管理SQLによるid変更は、前のidの削除と新しいidの追加として記録する。

## 取引の順序と制約

書き込み文の開始時に、取引単位のアドバイザリロック `(1414745932, 1)` を取る。
別行に触る取引も含めて直列化し、未確定の小さいseqを後から見落とすことを防ぐ。
ROLLBACKによるseqの欠番はあり得る。欠番を削除や読み込み失敗とみなさない。
ロックを手放すのは取引の終わり。本文の通常の読み取りはこのロックを取らない。

これは個人用アウトラインのための単純な方式で、書き込みの並列性は下がる。
500行単位の現在の送信を維持する。長い取引を避け、実データで待ち時間と容量を測ってから適用する。
将来のCAS用RPCでも、行ロックより先に同じアドバイザリロックを取る。
外部の管理処理が先に行ロックを取るとデッドロックになる場合がある。
PostgreSQLはその取引を取り消すため、呼び出し側は再試行を扱う必要がある。

履歴はDMLを対象とする。列の追加・削除などのDDLは別途整合性を確認する。
無効化したトリガー、表の作り直し、記録の手動変更を平常の状態として扱わない。
再適用時には元の表のOIDと本文・最新世代・履歴を照合し、不一致なら一括で中止する。
自動で履歴を消して整合させる処理は作らない。

## 権限

元のoutline_nodesのRLSと書き込み権限は維持する。
内部の記録処理だけをSECURITY DEFINERとし、検索パスをpg_catalogに固定する。
表・関数はすべてスキーマを明示し、利用者が作った一時オブジェクトを参照しない。
非公開スキーマ・表・シーケンス・内部関数はPUBLIC／anon／authenticatedへの権限を取り除く。
履歴の表にもRLSを有効にし、通常クライアントに公開するポリシーは作らない。
実行者はauth.uid()を記録するが、履歴を読む権限の根拠としてはまだ使わない。

このアプリの既存テーブルには文書の所有者列が無い。現在の「単一利用者」の構成だけで
履歴を全ログイン利用者に開放しない。閲覧・復元RPCを作る際に、文書の識別と所有権を決める。
非公開スキーマをSupabaseのExposed schemasへ追加しない。

## 本番へ適用する前と、問題が起きた場合

1. 端末別の控えに加え、サーバーのoutline_nodesを退避する。
2. SQLを検証用のSupabaseへ先に適用し、実際のロール・RLS・通常保存・全削除を確認する。
3. 容量と書き込みの待ち時間、DB側のstatement_timeoutを確認する。
4. 本番の書き込みを止め、DB管理者でSQLを1回の取引として適用する。
   ロックを5秒で取れなければ全体が取り消される。途中だけを手作業で続けない。
5. 本文とheadsの件数・内容を照合してから書き込みを再開する。

通常の削除後も文章が履歴に残る。保持期間・復元UI・完全消去の運用はまだ無い。
容量は増え続けるので、運用を決めるまでは本番に導入しない。
無効化する場合は書き込みを止めてから、下の3つのトリガーだけを1取引で外す。
元の本文や履歴の表・関数は消さない。

```sql
begin;
set local lock_timeout = '5s';
lock table public.outline_nodes in share row exclusive mode;
drop trigger if exists taskspace_outline_lock on public.outline_nodes;
drop trigger if exists taskspace_outline_capture on public.outline_nodes;
drop trigger if exists taskspace_outline_no_truncate on public.outline_nodes;
commit;
```

停止中の編集は記録されない。再開時は本文と履歴を照合し、食い違いを別の控えへ残してから
新しい基準を決める。トリガーの再作成だけで未記録期間が埋まったことにはしない。
過去のseqと世代を流用・初期化する復旧は行わない。

## 検証と次の段階

CIの使い捨てPostgreSQL 15／17で、初期控えと再適用、上書き前後、削除と復元、
取引の取り消し、記録失敗、権限、RLS、1万行、同時更新と確定順を確認する。
未記録の編集、履歴の欠落、本文の表の作り直しがある場合は再適用を中止し、本文と記録を保持することも確認する。
Supabaseのauth.uid()と認証ロールは試験用に置き換えるため、実サービスの検証とは区別する。
JSライブラリーは追加しない。SQL検証は既存DBと同じPostgreSQLのコンテナー内のpsqlで行う。

次は、読み込んだサーバー世代を条件に書き込むCAS用RPCと、再送の操作IDを用意する。
その後にクライアントの永続キューへ接続し、競合する双方の内容を画面から確認できるようにする。
